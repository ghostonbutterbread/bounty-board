# Bounty Board backend contract

## Run and security boundary

`python3 app.py [--config board.json|board.toml] [--root /absolute/path/to/Shared] [--port 9001] [--tailnet-host node.tailnet.ts.net [--tailnet-port 443]] [--bbh /absolute/path/to/bbh] [--accept-uncoordinated-writes]` requires Python 3.11+ and its Python code uses the standard library. Read-only operations and shared edits that need no merge do not require Git; three-way collaboration merges require an executable `git` on the server's `PATH` (`git merge-file`). Config is a JSON object or TOML top-level table with optional `root` (string), `port` (integer 1–65535), `tailnet_host` (canonical lowercase `node.tailnet.ts.net` DNS name), and `tailnet_port` (the Serve HTTPS port, integer 1–65535, default 443; any other port makes `https://<host>:<port>` the only trusted tailnet origin). Relative config roots are relative to the config file; CLI values override file values. Defaults are `~/Shared`, port 9001, and no tailnet host. Invalid files, keys or values fail startup. The root is the **parent** containing `web_bounty/` and/or `binaries/`. Metadata writes require both `--bbh` and the separate command-line acknowledgement `--accept-uncoordinated-writes`; either alone leaves them disabled. Neither can be supplied in config. Acknowledgement accepts lost-update risk, not a guarantee of safe writes.

The backend binds IPv4 `127.0.0.1` only; it has no remote-listen option, authentication, TLS or CORS. By default it accepts only `Host: 127.0.0.1:<port>` or `localhost:<port>`. Explicit tailnet opt-in additionally accepts the exact hostname with no port or `:443` and, when present, the browser-serialized `Origin: https://<hostname>` (default HTTPS port omitted); local origins must exactly equal `http://<host>`. One Host is required, and duplicate Host, Origin, or Sec-Fetch-Site headers are rejected. GET permits absent, `none` or `same-origin` Fetch Metadata; other values, including `same-site` and `cross-site`, are refused. Origin is optional for GET, mandatory for PATCH. There is no wildcard and no trust in forwarded headers. These checks are defense in depth against browser cross-origin access, **not authentication**; non-browser clients can forge them. Other local processes can read the server.

For an explicitly configured deployment, Tailscale Serve terminates HTTPS and enforces tailnet network policy; any permitted tailnet device can read sensitive API output. First review policy, DNS/certificates and existing Serve routes; then, for example, `tailscale serve --bg --https=443 http://127.0.0.1:9001`. This changes Serve configuration; do not use Funnel or public exposure. Run without the optional collaboration and writer flags for read-only operation; report source writes require explicit autosave opt-in. Localhost HTTP and tailnet HTTPS are separate browser-storage origins, including drafts and preferences. API output can contain sensitive program names, findings, report text, URLs and evidence references; do not publish or log it. API responses include `Cache-Control: no-store`; successful static asset responses do not. Requests are not logged by the server.

The server serves `static/index.html` at `/`, and other files under `static/` at their corresponding URL paths. Filesystem paths, including symlinks, are not exposed through this static route. The HTTP server operates against live sources, not a globally atomic portfolio snapshot. Refresh to see external changes.

## `GET /api/data`

The ordinary request remains a synchronous full discovery. A read-only browser
may opt in to a first projection with the `X-Bounty-Board-Phase: summary` header
(or `?phase=summary`). Only servers with no configured metadata writer,
collaboration, source autosave, or fixture publisher honor this opt-in; all
others return the ordinary full response. The summary retains the usual
ledger/map/coverage data, sets every lane's `reports` to `null`, sets
`reports_loading: true` and `capabilities.source_authoritative: false`, and
does not advertise write capabilities. Report absence is not inferred during
this phase. The browser then requests `?phase=complete&root_instance=<token>`
once, and may request `?phase=identity` to recheck a deferred result. A root
instance token binds canonical root path, device and inode before and after
each phased scan; a mismatch returns 409. It is an opaque freshness check, not
a lock, authentication, content snapshot, or protection against every change
inside the root. An unavailable root uses the normal full response. If the
full request fails, the browser retains the summary and offers Refresh.
Refresh itself follows the existing full-load path. A focused control or draft
defers application until the user chooses it; the source identity is checked
again then. A newer Apply attempt supersedes earlier checks; navigation or
Refresh prevents an outstanding check from applying its snapshot. A failed
completion leaves report totals unknown, including for an empty summary.
Summary-scoped lazy MapStore and gadget observations include the root instance
and fail visibly on a changed root, without replacing the retained summary.
The projection still reads ledger, map and coverage synchronously,
so those sources can delay it; no production latency improvement is implied.

JSON shape (all collections are lane-scoped):

```json
{"programs":[{"id":"web_bounty/example","name":"example","family":"web_bounty","lanes":[{"name":"web","findings":[],"coverage":{"counts":{},"items":[],"total":0,"mapped_kinds":{},"unclassified_surfaces":0,"unassessed_surfaces":[]},"map":[],"gadgets":[],"reports":[],"warnings":[]}]}],"warnings":[]}
```

This is a structural example only, not a claim that an empty or missing source is complete. Discovery accepts `web_bounty/{program}/{web|api}` and `binaries/{program}/{apk|exe|mac}`, skips underscore-prefixed program housekeeping and symlinked family/program/lane directories. Program ID is `family/name`; lane name is the directory name. Other directories are not inferred to be programs/lanes.

* `root_identity`: lowercase SHA-256 hex of the canonical resolved root path, or `null` if the root is unavailable. Equivalent symlink/relative paths resolve to the same identity; different canonical paths get different identities. This is a stable namespace, not a secret: guessed paths can be hashed and compared. It contains no raw path or report content. Moving or renaming a root changes its identity. The root must remain stable while the server handles requests; this is not a snapshot or protection against concurrent filesystem replacement.
* `findings`: list from `ledgers/ledger.json` `findings`, or `null` if missing, malformed, unreadable, or over 5 MB. Each object selects `fid`, `type`, `title`, `class_name`, `severity`, `severity_rationale`, `status`, `current`, `review_tier`, `submission`, `submission_status`, `platform_outcome`, `file`, `report_dir`, `report_path`, and `evidence_path`; absent values are `null`, except that `title` falls back to recorded `type`. `status` uses the non-empty top-level field first, then `current.status`; the original `current` is also preserved, so conflicting source fields remain visible. `file` is the affected source/asset, not a report; the report fields are recorded filesystem references and may be absolute. The BBH submission object, where present, has distinct `state`, `result`, and optional `report`; do not infer submission or duplicate outcome from finding status, severity, a draft, or file names. Except for the status fallback, fields are displayed as recorded.
* `coverage`: live `ledgers/surface_coverage.sqlite`, or `null` on missing/unavailable/unsupported DB. `items` contains joined surface/class assessments: `surface_id`, `kind`, `host`, `surface_key`, `input_key`, `consumer`, `fingerprint`, `run_id`, `class_name`, `status`, `pressure`, `reason`, `boundary`, `axes`, `evidence_refs`, `reopen_when`, `assessed_fingerprint`, and `prior_status` when stale. `freshness` describes the fingerprint comparison: `current`, `stale`, `unknown` (either side missing), or `not_applicable` for `no_assessment`; it is not a claim that a surface is completely tested. The BBH legacy `untested` and `exhausted` statuses are shown as `no_assessment` and `bounded_review`; known fingerprint/run mismatches become `stale`. `counts` count these questions, `total` is their sum, `mapped_kinds` counts mapped surfaces, and `unclassified_surfaces` counts mapped surfaces with no assessment question. `unassessed_surfaces` lists those surfaces' identities and metadata; unlike `no_assessment`, they have no assessment row. All are read in the same SQLite snapshot. Missing/empty coverage is not evidence of exhaustive mapping. SQLite opens with `mode=ro`, **not** `immutable`, so committed WAL transactions remain visible; SQLite's normal read-only WAL shared-memory coordination applies. The static source-file `coverage.json` is intentionally not conflated with live coverage.
* `map`: list from `recon/maps/map.jsonl`, with `title`, `url`, `surface`, `scope`, `status`, `path`, `tags`, `timestamp`; `null` means missing/invalid/unavailable or over 5 MB. `gadgets` is the subset whose tags contain `gadget`, including residual and archived observations; it is not a list of confirmed exploits. Observation bodies are not included in this response; they are loaded on demand. Application-behavior indexes are not loaded.
* `reports`: list of `{path,name,kind,owner_fids,editable,collaboration_editable}` for Markdown files recursively under `reports/`, with `path` relative to that directory. **Evidence files are not listed** (feat/board-evidence-artifacts): a Markdown file is evidence, an artifact of its finding, when no ledger `report_path` names it and either its name is `EVIDENCE.md` (any case, any depth) or a ledger `evidence_path` names it (relative `reports/...`, or absolute matched under this lane or by its `/<family>/<program>/<lane>/reports/` segment). The shared classifier is `report_evidence.is_evidence`; evidence is skipped before its content is read. Its content stays available from `GET /api/report` and its folder from `/api/report-artifacts`. `registered_report` means an exact path matches a ledger `report_path` (a `report_path` named `EVIDENCE.md` stays a report); `generated_evidence` is no longer produced (older clients may still map it); `generated_navigation`/`generated_report` are identified by BBH markers. Otherwise it is `unregistered`, or `unknown` when the ledger is unavailable or the content cannot be read, decoded or is over 5 MB. Exact ledger ownership still identifies registered reports even if content is unavailable. A content failure adds lane warning `report_content_unavailable_or_invalid`. Owners come only from exact recorded paths; basenames are never joined. `owner_fids` may have multiple entries and is empty for unregistered/unknown paths. `editable` is true only for readable eligible sources when report autosave is enabled; `collaboration_editable` is true for readable eligible sources regardless of source autosave. Generated navigation and seeded placeholders are ineligible; ordinary registered/unregistered reports are eligible (`GET /api/report` still reports evidence as eligible; the Board opens evidence read-only). Both are point-in-time observations, not guarantees against subsequent source changes. Symlink files and directories are skipped. `null` means the directory is missing or unusable; warnings signal a partial directory traversal. Content is loaded separately.
* **One report per finding packet** (feat/board-one-report-per-packet, `docs/integrations/report-packets.md`). A packet is a folder directly under `reports/` named `<FID>` or `<FID>-<slug>`. The shared helper `report_packets.plan` (also used by the search index) picks one *main report* from the packet's top-level non-evidence `.md` files: vuln-type `<prefix>-<FID>.md` (3+ hyphen tokens, no `.`, first token not a sidecar word), then `SUBMISSION.md`, `SUBMISSION-<FID>.md`, old FID reports (`REPORT.md`, `<FID>-REPORT.md`, `REPORT-<FID>.md`, `<FID>.md`), then any other; within a tier a ledger `report_path` wins, then newest mtime, then name. The main item adds `packet` (folder), `packet_main` (itself), `modified` (newest regular file in the packet, excluding dot names, `*.tmp` and `_meta/`), `file_modified` (its own mtime), `updated_file` (packet-relative newest file when not the main, else null) and `packet_evidence` (evidence paths in the packet); its `owner_fids` include every finding whose `report_path` lies in the packet, so it is `registered_report` when any does. Every other `.md` in the packet (any depth, `_meta/` excepted) and a legacy `findings/<bucket>/<FID> - <title>.md` copy of a finding with a packet main is listed with `kind: "packet_file"`, `packet`, `packet_main`, `packet_group` (`files`, `archive` for paths under an `_` folder, `older` for legacy copies), its own `owner_fids` and `modified`; it is never read for the listing (`editable` follows autosave, `collaboration_editable` is true). Clients leave packet files out of lists, pickers and counts. Ledger paths resolve through `report_evidence.reports_relative`, so a `reports/../reports/x.md` or another host's absolute path now registers its file.
* `warnings`: strings describing missing or unavailable sources. Top-level `root_unavailable` and `discovery_incomplete` distinguish an unavailable/partially read tree from an authoritative empty portfolio. Lane warnings include `ledger_missing`, `map_missing`, `coverage_missing`, `reports_missing`, and corresponding `*_unavailable_or_invalid`. `null` means unknown/unavailable, never zero.

Dashboard submission aggregates count each finding at most once per field: nonempty `submission.state`/`submission.result` take precedence; otherwise `submission_status`/`platform_outcome` are used respectively. Missing values are not inferred from finding status. Dashboard filters scope all aggregates to the selected program or all programs; incomplete source collections are labeled and totals shown as unknown. Dashboard and workspace program selectors display the full program ID, including its family.

SQLite kind values are grouped under their JSON object-name spelling in `mapped_kinds`: strings retain their text, while numeric and null values use their JSON spelling. Groups with the same spelling are summed (for example, integer `1` and text `"1"` share one count), so counts are retained but the original SQLite types cannot be recovered from this aggregate. Excessively nested ledger, MapStore or assessment JSON that the runtime cannot decode or encode, and ledger values that cannot be encoded as UTF-8 or standard JSON, are unavailable at their own source boundary, with the normal lane warning; other sources and lanes remain readable.

`capabilities` explicitly advertises `finding_metadata` (boolean), `finding_fields` and `finding_options` (severity/status lists), plus `report_edit:false`. `finding_metadata_warning` is always a human-readable warning that uncoordinated metadata writes can overwrite concurrent edits, including other hosts and sync clients, and that no shared compare-and-swap exists. Without acknowledgement, `finding_metadata` is false, fields/options are empty, the writer is not probed or invoked, and PATCH is disabled. Missing or failing BBH also disables metadata writing without disabling reads. This server has no search indexing, fabricated metrics, submission inference, or current-agent activity; an explicitly configured collaboration directory holds shared drafts and history.

## `GET /api/map-observation?family=web_bounty&program=example&lane=web&path=_app%2Fexample%2Findex.md`

This read-only endpoint re-reads the selected lane's current `recon/maps/map.jsonl` and requires exactly one entry with an exact relative `path` match. All four query selectors must occur once. An optional `root_instance` may occur once; when supplied, the server checks the current root instance before and after the index/body read and returns `409 {"error":"root_changed"}` on a mismatch. A request without this optional parameter retains the ordinary full/writer-mode behavior. These checks are not an atomic filesystem snapshot, do not detect every same-inode internal change or ABA replacement, and cannot prevent a swap after the final check. The selected index and body are opened componentwise without following symlinks, bounded at 5 MB each, and must be regular files containing UTF-8. The body path must end in `index.md` and cannot contain empty, dot, traversal or absolute components. An invalid, unavailable or ambiguous index, unindexed or unsafe path, missing body, wrong lane, bad UTF-8 or oversized file returns `404 {"error":"observation_not_found_or_unavailable"}` with no filesystem path. Success returns `200 {"content":"<exact UTF-8 text>"}`. The current index and body are not an atomic snapshot against concurrent writers. The interface displays body text inertly, not as rendered HTML or links; it makes no inference about free-form capability fields or whether a gadget is confirmed.

## `PATCH /api/finding`

Enabled only with both a functioning, explicitly selected `--bbh` executable and `--accept-uncoordinated-writes`. Example body:

```json
{"family":"web_bounty","program":"example","lane":"web","fid":"D01","root_instance":"<root_instance from GET /api/data>","expected_revision":"<metadata_revision from the displayed finding>","patch":{"severity":"HIGH","class_name":"ssrf","status":"dormant","severity_rationale":"Verified boundary"}}
```

Only the four shown patch fields are accepted; patch is nonempty and all values are strings of at most 4000 characters. Severity and status must match advertised options exactly; `class_name` matches `[a-z0-9][a-z0-9_.-]{0,99}`. FIDs match `[A-Za-z][0-9]{2,}` and must exactly match one unique, case-insensitively unambiguous ledger FID. Program names match `[A-Za-z0-9][A-Za-z0-9._-]*` and must name the existing lane. This narrower write contract does not hide other records in reads. Submission/result are not editable here; see `POST /api/finding/submission`, which runs BBH's `--set-submission`.

Requires exactly one trusted `Host` (loopback or the explicitly enabled tailnet host), matching `Origin`, `Content-Type: application/json`, `X-Requested-With: Bounty-Board`, no transfer encoding, and absent or `same-origin` Fetch Metadata. Duplicate Host, Origin and Fetch Metadata headers are rejected. This protects against browser cross-origin requests and DNS rebinding, **not other local processes or permitted tailnet clients**. Body limit is 16 KiB. Filesystem preflight rejects unsafe links in BBH output/layout paths, but the data tree must be trusted against concurrent hostile local replacement.

The server invokes the configured BBH `agents/manual_hunter.py` with explicit family, lane, root, exact FID and temporary JSON patch, never through a shell. The BBH writer uses `EVIDENCE_ONLY`, refreshes generated navigation/indexes and may create/update context files; it does not regenerate finalized report content. The server rereads the ledger and verifies all requested values (including `current.status` if present) before returning `200 {"finding":...}`. It does not directly edit the ledger. A BBH failure or post-write verification failure disables writes for this server process; restart only after diagnosing. Failures after invocation may be partial: refresh the source before retrying. `400 invalid_finding_patch`, `403 untrusted_origin`, `404 finding_not_found`, `409 unsafe_writer_tree`, `502 writer_failed`/`verification_failed`, and `503 writer_unavailable` are possible.

The root instance and finding revision are required on every write, including direct API calls. The opaque finding revision binds the exact source finding to its lane; a fresh read before invocation returns `409 finding_changed` if it differs and `409 root_changed` if the root instance changed. Missing or malformed preconditions return 400. The board serializes its own requests in one server process; a missing finding returns 404. The precheck is **not an atomic compare-and-swap**: a BBH process, another Board server, editor, or synced peer can write after the check, and transient/ABA changes may be missed. Stop other writers, including sync activity, and refresh before editing; the operator still accepts residual risk. The startup `--help` probe detects basic runtime availability, not full compatibility, and successful read-back is a point-in-time observation, not an ongoing lock.

A successful `200` response also carries `revisions`: `{fid: [old, new]}` for other entries in the same lane whose stored JSON the write left byte-for-byte unchanged. BBH replaces `ledger.json` atomically, which changes every revision (the revision includes the ledger file identity). A client may replace a row's revision with `new` only if it holds exactly `old`; entries changed by anyone else are omitted and still conflict. This applies to every ledger action below.

## Ledger actions: `POST /api/finding/submission`, `/api/finding/new`, `/api/finding/reclassify`

Same enablement, headers, body limit, root/revision preconditions, filesystem preflight, metadata lock, verification and disable-on-failure rules as `PATCH /api/finding`. Each action is advertised in `capabilities.ledger_actions` only when the BBH writer's `--help` output lists the options it needs; otherwise it is `{"enabled": false}` (reclassify also gives a `reason`) and the endpoint returns `503 writer_unavailable`. Errors: `400 invalid_ledger_action`, `403`, `404 finding_not_found`, `409 root_changed`/`finding_changed`/`unsafe_writer_tree`, `502 writer_failed`/`verification_failed`, `503 writer_unavailable`, plus the action-specific ones below.

- **Submission** body: `{family, program, lane, fid, root_instance, expected_revision, submission: {state, result?, report?}}`. `state` is `not_submitted|submitted|dropped`, `result` is `valid|duplicate`, `report` is 1-200 printable characters. Runs `manual_hunter.py --set-submission FID --submission-state S [--submission-result R] [--submission-report REF]` and verifies `finding.submission`. It only records local state; nothing is sent to any platform. BBH cannot clear a recorded result; an omitted result or reference keeps the recorded value.
- **New finding** body: `{family, program, lane, root_instance, finding: {title, class_name, severity, file, description}}`, all single-line strings; `severity` must be an advertised severity. The server writes a temporary `Label: value` note and runs `manual_hunter.py --from-file`. It verifies exactly one new FID with the same title and class. BBH's documented duplicate outcome (`Duplicate:` on stdout, exit 1, ledger bytes unchanged) returns `409 not_added` and leaves the writer enabled.
- **Reclassify** body: `{family, program, lane, fid, root_instance, expected_revision, destination: "gadgets"|"map", details: {title, surface, note?, tags?, archive_original?, tier?, capability?}}`. Gadgets need `tier` (`confirmed|residual`) and a capability block (`grants`, `requires`, `crosses`, `chain_status` in `ready|deferred|watch`, optional `crosses_detail`/`chain_watch`; residuals also `residual_class`, `disclosed_by`, `composes_with`), matching the BBH map-store gadget policy. Step 1 runs `agents/map_store.py write --scope surface --tags gadget[,residual],finding-<fid>,from-ledger[,extra] --agent bounty-board --body-file ...`. The body records the source FID, title, class, severity, evidence and report paths. Step 2 runs `manual_hunter.py --edit-finding` to append a pointer line to `review_notes` (and set `status: archive` if asked). The finding, its severity, evidence and report files are never removed. If a MapStore entry tagged `finding-<fid>` already exists, the server returns `409 already_reclassified` without invoking BBH. If the finding changes between the steps, it returns `409 partial_reclassify` with `map_entry` and does not annotate. Success returns `{finding, map_entry, revisions}`.

## `POST /api/finding/delete` (permanent delete of an archived finding)

Body: `{family, program, lane, fid, root_instance, expected_revision}`. Same headers, body limit, lane/FID validation, root/revision preconditions, filesystem preflight, metadata lock and disable-on-failure rules as the ledger actions above. Advertised as `capabilities.ledger_actions.delete = {enabled, requires_status: "archive"}`, enabled only when `manual_hunter.py --help` lists `--delete-finding`; otherwise `503 writer_unavailable` without invoking BBH. The server refuses with `409 not_archived` before invoking BBH unless the finding's current status is exactly `archive` (the UI first sets `archive` on a finding marked `archived`). It runs `manual_hunter.py <program> --family F --lane L --root ROOT --delete-finding FID [--actor bounty-board]` (`--actor` when the help lists it) and verifies that the FID is gone from the re-read ledger.

BBH's delete is permanent: it removes the finding, deletes its generated report files and keeps only a minimal tombstone (FID and identity) so later runs do not re-add it. There is no restore; archive is the recoverable state. Exit codes: 0 deleted; 1 refused before commit, relayed as `409 delete_refused` with `reason` (the stderr `[manual_hunter] ...` text, for example "it is the highest FID of its prefix ...") and the writer stays enabled when the ledger is unchanged; 3 deleted but a later step warned, a verified success with `warnings: true` and `warning_text` (the `Warning:` lines, at most 5, 300 characters each); 2 (usage) or anything else disables the writer (`502`). Success: `{deleted: fid, warnings, warning_text, revisions}`.

## Finding status values and `GET /api/archive-state`

`capabilities.finding_options.status` offers `raw, confirmed, active, pending-review, dormant, novel, complete, archive` (Bounty Core's default status is `active`). `PATCH /api/finding` accepts any safe status token (`[a-z0-9][a-z0-9-]{0,39}`; BBH accepts any string), so Restore and Undo can write back a finding's exact previous status, for example `closed`. The UI treats `archived` like `archive`.

When `PATCH /api/finding` moves a finding into `archive`/`archived`, the server records `{family, program, lane, fid, previous_status, archived_at}` in its private state directory (`--state-dir`, default `~/.local/state/bounty-board`, refused if inside the data root) as `archive-state.json`: one atomic file replace per change, at most 5000 entries (oldest dropped), never in the ledger. The response adds `archive_state: saved | no_previous_status | unavailable`. Moving the finding out of archive, or deleting it, forgets the entry. `GET /api/archive-state?family=&program=&lane=` (same trust checks as every GET; exactly these three parameters) returns `{available, entries: {fid: {previous_status, archived_at}}}`; `available: false` when the server has no state directory.

## `GET /api/report?family=web_bounty&program=example&lane=web&path=raw%2Fexample.md`

On success: JSON `{ "content": "<UTF-8 Markdown>", "revision": "<sha256 hex of exact file bytes>", "editable": true, "collaboration_editable": true }` for an eligible report with autosave enabled, and HTTP `ETag: "<same sha256 hex>"`. With autosave off, `editable` is false even when `collaboration_editable` is true; generated navigation has both false. Treat revision as opaque. The path is relative to the selected lane's `reports/`, must name an existing `.md` file, and all components are opened without following symlinks. Traversal, absolute paths, symlinks, malformed/non-UTF-8/oversized files, and unavailable paths return `404 {"error":"report_not_found_or_unavailable"}`. Bytes are limited to 5 MB. Refresh this endpoint to observe an external edit; revisions are content hashes, not locks.

Other than the opt-in collaboration endpoint below, report-edit requests are disabled. The ordinary report endpoint remains read-only.

If a collaboration merge needs Git but `git` cannot be started, the API returns `503 {"error":"git_unavailable", "message":"..."}`. Retain the local draft, restore an executable Git to the server's PATH, and retry the same request ID; inspect the result. A failure during post-publication observation instead retains the existing `outcome_uncertain` contract because a source exchange may already have happened.

## `GET /api/recent-reports?limit=50&offset=0&within=604800&program=web_bounty%2Fexample&lane=web&q=xss&order=newest&nav=0`

Read-only. Reports across every program and lane ordered by file modification time, served from the background search index (same safe walk: no symlinks, `_`-prefixed programs skipped). All parameters are optional: `limit` 1 to 200 (default 50), `offset` 0 to 1,000,000, `within` seconds before the server's now (1 to 20 years), `program` repeatable up to 100 times (`family/name`), `lane` one of the known lanes, `q` up to 200 characters (every term must occur in the title or path, case-insensitive), `order` `newest` (default) or `oldest`, `nav` `1` to include generated navigation stubs. Anything else returns `400 {"error":"invalid_recent_reports"}`; more than four concurrent search or recent requests return `503 {"error":"search_busy"}` with `Retry-After: 1`. Same Host/Origin/Fetch Metadata checks as every GET.

Response: `{index_state, root_instance, now, total, total_reports, offset, limit, order, items, facets, warnings, took_ms}`. Each item: `path` (the report id used in routes), `name`, `title` (first heading or file stem), `program` (`family/name`), `program_name`, `family`, `lane`, `modified` (Unix seconds, float), `report_kind`, `owner_fids`, `finding` (`{fid, severity, title}` of the first owning finding in the ledger, or null) and `target` (`{program, lane, section:"reports", report}`). `facets.programs` and `facets.lanes` count matches, each ignoring its own filter. While the index builds, `index_state` is `building` and results may be partial. A request finds the index at most one refresh interval (5 s) old: an older index is refreshed once first (bounded 2 s wait).

Lane report entries in `/api/data` and `/api/lane-reports` also carry `modified` (Unix seconds, float, or null).

**One row per finding packet (feat/board-one-report-per-packet).** Items, `total`, `total_reports`, facets, paging and the `within` window count packets, not files: a packet appears once, as its main report (rules under `/api/data` `reports`), with `modified` set to the newest regular file in the packet. Items add `packet` (folder or null) and `updated_file` (packet-relative path of that newest file when it is not the main report, else null). The row maps to the finding whose `report_path` lies in the packet (`match: report_path`), else the packet FID (`match: packet`). N/A follows the main report's mark; marks on packet files are kept and ignored. Packet files are never search report hits and finding hits link the main report.

**Finding mapping and N/A (feat/board-recent-actions).** `item.finding` is now the finding the report belongs to, computed from the already-loaded ledger when the index scans the lane (no extra disk walk), in this order: the finding's `report_path`, a BBH packet folder (the first path segment is `<FID>` or `<FID>-<slug>`, e.g. `F012-xss/acme.example-xss-F012.md`, `F012-xss/_meta/notes.md`), or a legacy file named `<FID> - <title>.md` at any depth. New parameter `hide_na` (`0` default, `1`). Each item carries `na` (bool). The response adds `na_available` (false when the Board has no state directory or `report-na.json` cannot be read; then no item is marked), `na_hidden` (N/A reports left out by `hide_na=1` that match every other filter) and `na_hidden_page` (those whose sort position falls within the returned page: after the previous page's last visible item, up to and including this page's last item; the dashboard shows it as "N hidden"). With `hide_na=1`, totals, paging and facets count visible reports only.

## `GET /api/recon/overview` and `GET /api/recon/program?family=web_bounty&program=example&lane=web[&refresh=1]`

A failing source never fails the response.

Every count is `{value, approximate, method?}`. `approximate: true` with `method` `max_id` (AUTOINCREMENT high-water mark, an upper bound when rows were deleted), `sample_scaled` (rowid-window sample scaled to the total), `skip_scan_partial` (index enumeration stopped by the budget) or `size_scaled` (a line count extrapolated past the 64 MiB read cap). Timestamps are Unix seconds (`last_activity`, `computed_at`) or the source's ISO-8601 text.

Overview: `{computed_at, partial, artifact_root: {configured, path, available, message?}, budget, programs: [{id, family, program, lane, urls, routes, hosts, parameters, param_urls, test_runs, tested_urls, tested_params, tests_recent: {last_24h, last_7d, all}, observations, js_files, js_bytes, js_source_maps, js_observations, js_open, js_leads, js_urls, aggregates, js_lists, findings, findings_by_severity, coverage_questions, last_activity, states, approximate}]}`. Program: `{computed_at, partial, family, program, lane, lanes, lane_path, headline (an overview row), sources (each with result: depth numbers plus detail: hosts, coverage_matrix, observation_groups, recent_tests, recent_observations, untested_params for the URL index; hosts, source_map_files, largest_files, signals, lens_counts, recent_observations, open_observations, leads for the JS library), hosts: {rows, total, truncated, urls_approximate, rule}, artifact_root, budget}`. Host rows add `js_files`, `js_bytes`, `findings` (non-archived findings whose `asset`/`url`/`endpoint` names the host), `coverage_questions`, `coverage_reviewed`, `under_tested` and `surface_score`; at most 300 rows (highest surface first). Lists are capped at 50 rows, grouped breakdowns and per-host joins at 500 and tested (lane, parameter) pairs at 5000, with capped sections named in the source result's `truncated` object; text fields at 240 characters (URLs 600). Every string is display-safe: C0, DEL, C1, U+00AD, U+061C, U+200B–200F, U+202A–202E, U+2060–2069, U+FEFF, U+2028 and U+2029 are escaped as `\xNN`/`\uNNNN`, and items (parameters, hosts, URLs, JS observations and leads, program and lane) whose raw value contained one carry `unsafe_chars: true`, meaning the value must not be copied or linked.

Computation runs on one background thread. A request returns immediately with whatever is cached; `partial: true` means at least one source is still computing (poll; the UI polls every 1.5 s). Results are cached per source keyed by the file signature (size and mtime of the database and its `-wal`); a changed source is served `stale: true` and recomputed at most every 120 s, or at once with `refresh=1`. Reads never create or leave files next to a database: WAL databases with no WAL content (no `-wal`/`-shm`, or an empty `-wal`) open `file:…?mode=ro&immutable=1`; a non-empty `-wal` with an existing `-shm` (active writer) opens `mode=ro`; other WAL states are not opened (`unavailable`, "writer state unclear"); rollback-journal databases open `mode=ro`. All connections use a 1 s busy timeout and `PRAGMA query_only=1`; every statement is interrupted after the per-query budget (`--recon-query-budget`, default 3 s; progress handler plus an interrupt watchdog). Tables above 200,000 rows are never aggregated in full. JS library `downloads/`, `chunks/`, `sourcemaps/` and `ledger.json` are never read. `--artifact-root PATH` selects the artifact tier (default `/mnt/bounty` when it is a mount point, otherwise none).

Scope (`scope_check.py`; contract and decisions: `docs/integrations/scope-check.md`). On `failed`/`unconfigured` every verdict is `unchecked` with a reason starting `scope check failed:`; on `no_scope` the reason is `no scope on file` (open scope). Overview rows add `scope` (the same summary with counts over the URL index host list), `in_scope_urls` and `in_scope_js_files` (`method: host_counts` when a program view cached per-host counts, else `host_share`: the total scaled by the in-scope host share, approximate; `null` unless `checked`). Verdicts are cached in memory per program under a stat-only signature of the scope files; a cached request starts no subprocess.

## `GET /api/scope?family=web_bounty&program=example[&refresh=1]` (scope panel)

Read-only (`scope_inventory.py`; contract and decisions: `docs/integrations/scope-panel.md`). `family` must be a Board family; `program` is a directory name (no `/`, `.`, `..` or NUL, at most 200 characters); anything else is `400 invalid_scope_request`. Reads `<root>/scopes/<program>/` (an alias link only when it resolves inside `<root>/scopes`), never writes, never fetches. Response: `{version: 1, family, program, copy_safe, computed_at, stale_days: 7, scope: {state: loaded|none|failed, reason, alias?}}`; `none` (no scope directory: open scope) and `failed` (broken or escaping alias) carry nothing else. `loaded` adds:

- `files`: per file `{state: ok|missing|too_large|invalid|unreadable, error?, size?}` for `scope-pull.json` (cap 64 KiB), `scope-items.json` (4 MiB), `in-scope.txt`, `out-of-scope.txt` (1 MiB each), `program-policy.md` (256 KiB) and `scope-history.jsonl` (only the last 256 KiB is read). A bad file never fails the response; a file that is a link resolving outside `<root>/scopes` is `unreadable`.
- `freshness: {pulled_ts, pulled_at, estimated, source: scope-pull.json|assets.json|in-scope.txt|null, age_days, stale, failed, last_attempt_status, last_attempt_at, last_error, platform}`. `stale` is `age_days >= 7` or an unknown pull time; without a `pulled_at` the time is the `assets.json` or `in-scope.txt` mtime and `estimated` is true.
- `inventory: {state: ok|missing|invalid|too_large|unreadable, source, generated_at, count, truncated, skipped}`.
- `rules: {source: inventory|txt|none, in: {items, count, truncated}, out: {...}}`: identifiers of `enforced` inventory items, else the non-comment lines of the text files (up to 1000 items sent per list; counts exact).
- `policy: {text} | null`: `program-policy.md` with unsafe characters escaped per line; the client renders it with its safe Markdown subset.
- `assets`: inventory items of kind `android_app`, `ios_app`, `executable`, `source_code`, `cloud`, `other` or an unknown kind: `{key, kind, known_kind, identifier, name, in_scope, tier, max_severity, eligible_for_bounty, enforced, platform_type, description, first_seen, last_seen, release, lane}`. Times are `{text, ts}`. `lane: {program: "binaries/<program>", lane, updated_ts} | null` names the first existing, non-symlink binaries lane for the kind (`apk`, `exe`, `ios` then `app`) among the lanes the Board discovers; `updated_ts` is the newest mtime of its top-level regular files (stat only, first 10,000 entries). `release` adds `lane_stale: true` when `changed_at` is newer than `updated_ts` (or the lane has no top-level files).
- `history: {entries, more}`: the last 20 lines of `scope-history.jsonl`, newest first; each `{state: ok, at, source, added, removed, changed, release_changed, <list>_count}` (up to 200 items per list) or `{state: invalid, error}` for an unreadable line.

Every string is display-safe (control, bidi and invisible characters escaped as `\xNN`/`\uNNNN`); unknown keys are ignored. `copy_safe` is false when the raw program name had such characters; the client then disables copy. Parsed files are cached per program by `(st_ino, size, mtime_ns, ctime_ns)` of every file and the directory; ages and lane times are computed on each request. `refresh=1` reparses.

## `GET /api/recon/urls` and `GET /api/recon/url` (URL browser)

Read-only, same trust checks as every GET, lane resolved from discovery only, opened through the recon reader (`open_plan`/`ReadOnlyDB`: never creates side files, every statement under the query budget). At most two URL queries run at once; more return `503 {"error":"recon_busy"}`.

`GET /api/recon/urls?family=web_bounty&program=example&lane=web[&host=&q=&test_lane=&status=&params=1&param=&order=desc|asc&cursor=&limit=]`: one keyset page, newest first (`order=desc`, the default) or oldest first (`order=asc`). `host` exact host; `q` text anywhere in the URL (case-insensitive for ASCII, `%`/`_` literal); `test_lane` a lane (`[a-z][a-z0-9-]*`); `status` one of `untested`, `tested` (no / any test run, in `test_lane` when given), or a BBH status `discovered`, `surface_reviewed`, `deep_reviewed`, `validated_signal`, `dismissed` (the latest observation per lane); `params=1` URLs with query parameters; `param` URLs whose parameter keys include that exact name; `cursor` 0 (default) starts at the newest (or oldest) URL, otherwise the page holds ids below it (desc) or above it (asc); `limit` 1 to 100 (default 50). ## `POST /api/recon/mark` (BBH url_ingest.py mark)

Records one URL review through BBH: `agents/url_ingest.py mark <program> --url=<url> --lane=<test_lane> --status=<status> --agent-id=bounty-board [--param=<key> --param-location=<loc>] [--notes=<text>]` (argv list, no shell, `=` form so no value is read as an option). Needs `--bbh` with `--accept-uncoordinated-writes` and the `url_mark` writer feature (probed from `url_ingest.py --help`); `capabilities.ledger_actions.url_mark` advertises `{enabled, statuses, lanes, locations, board_lane: "web"}`. Same request rules as the ledger actions: same-origin `Origin`, `X-Requested-With: Bounty-Board`, `Content-Type: application/json`, at most 16 KiB, serialized with the metadata writes.

Body: `{family: "web_bounty", program, lane, root_instance, url_id, url, test_lane, status[, param[, param_location]][, notes]}`. `test_lane` one of BBH's lanes (`recon xss sqli ssrf idor lfi access-control ssti open-redirect xxe race csrf`), `status` one of the five BBH statuses (BBH prints an error and exits 0 for others, so the Board refuses them), `param` up to 120 characters, `param_location` one of `query body header cookie path json` (only with `param`), `notes` one line up to 500; no value may contain control, bidi or invisible characters. Runs that agents add to the same URL meanwhile are ignored, so they do not make a successful mark look failed (BBH would insert a new URL when the URL did not match; that fails the check). The lane's URL index summary is recomputed at once for a mark that follows no other within 2 s; marks closer together than 2 s (a bulk mark) share one recompute that runs 2 s after the last of them, so the summary is current at the end without a full recompute per mark. BBH has no delete; the Board offers none.

## Experimental collaboration source autosave (default off)

This branch is a **synthetic-tested prototype, not approved for real deployment**. `--collaboration-dir PRIVATE --report-autosave` enables synchronous publication on accepted collaboration POSTs; the switches are not configuration-file options. `--experimental-fixture-publish` is separate and mutually exclusive. The private store and source must be on the same filesystem. `GET /api/data` advertises `capabilities.report_autosave`.

A normal `POST /api/collaboration` with `base`, `content`, and unique `request_id` first commits the submitted version to the private SQLite store and performs the existing three-way merge against the observed source. When autosave is enabled the JSON includes `store_saved: true` and `publication.state`: `published`, `conflict`, `capacity`, or `outcome_uncertain`. `published` means exchange, directory fsync and current inode/content inspection succeeded; it is not a guarantee that external editors, older open descriptors, or sync will not change the file later. `conflict` can mean a collision detected **after** a visible exchange: never imply that the file was untouched. An `operation` is an opaque recovery handle; a capacity-refused handle need not have an operation directory. An unresolved store conflict prevents publication. The store may be saved even if publication or observation fails; retain the request ID and local draft. The call is synchronous: no `pending` receipt is currently supplied. Network failure is not confirmation of either store or file save.

`GET /api/collaboration/recovery` with the normal report identity and `request_id` returns the current store version, original `store_receipt`, and a fresh `publication` inspection; it never republishes. Unknown request IDs return 404. An interrupted publication attempt is `outcome_uncertain`; do not retry with a new ID blindly. If a stored request has no publication attempt, recovery reports `conflict`/`not_published` (or `outcome_uncertain` while retained reconciliation is incomplete). Exact POST retry uses the store's original receipt and reports a fresh publication assessment. The one exception to no-new-exchange on retry is a durable `capacity` refusal: because it occurred before operation creation and exchange, an exact retry may publish after capacity is increased, but only if the source snapshot and shared head still match and reconciliation is complete with no unresolved conflicts. Stop and retain the private operation for manual review when uncertain.

With autosave enabled, ordinary collaboration GETs, POSTs, history and recovery inspect retained operations in creation order and record newly observed snapshots in history. Successful responses include `reconciliation: {state: "complete"|"backlog"|"uncertain", scanned: N}`. A sweep examines at most 64 operations per interaction; a backlog advances on subsequent interactions, and POST returns HTTP 503 `retained_scan_backlog` without accepting the submission until its sweep completes. A sweep that finds an incomplete or uncertain publication reports `uncertain` and prevents further automatic exchanges, even when the new draft is saved to the store. Progress is per server and resets on restart; a multi-request sweep is not an atomic snapshot. If scanning fails, HTTP 503 `retained_reconciliation_unavailable` means retain the local draft and retry. Observed identical consecutive snapshots do not duplicate events; intervening versions may be missed. If a retained edit conflicts or leaves the store head different from the visible source, publication is reported as `conflict` and no automatic follow-up exchange is performed. The store receipt's content remains the original request result; use a fresh GET for the current reconciled head. For a divergent shared head, the UI offers a preview of both the current Markdown snapshot and the merged shared report, then a separate **Save merged report** action. Conflict resolution first saves to the shared store only, requiring that separate preview and confirmation when publication is still needed. `GET /api/collaboration` supplies `source_snapshot` when the source is present. An explicit POST uses `{ "action": "reconcile", "base": <expected shared revision>, "content": <exact shared text>, "source_snapshot": <exact observed Markdown>, "request_id": <new unique ID> }`. The server rejects stale snapshots, changed heads, unresolved conflicts and incomplete/uncertain scans. Its stored receipt binds the source snapshot too; exact retries do not perform another exchange except after a durable capacity refusal as described above. On `reconciliation_changed`, refresh and review; an ambiguous network outcome instead requires original-request inspection. If a sweep spans multiple requests, its completed result can be consumed once by the next explicit reconcile after checking that no new publication operation was added; a later scan can still discover old-descriptor edits made after their earlier observation. This is not a CAS.

Each operation retains a separate board copy, the initially observed inode, and the exchanged-out inode, in owner-only private storage. This content is plaintext and has no automatic cleanup. A preflight defaults to 1,000 retained directory entries and a 1 GiB free-space floor; `--retention-max-operations` and `--retention-min-free-bytes` override these limits. `capacity` means this attempt saved the shared draft but did not create an operation or exchange Markdown; the operation handle identifies the request, and `reasons` contains `retention_capacity`. The check includes crash remnants, reads filesystem available space, and reserves nothing. It is not a byte quota: existing inodes and other files can grow afterward. See README for operator backup guidance and limitations. Linux `renameat2(RENAME_EXCHANGE)` is required; unsupported/cross-filesystem cases fail without ordinary-rename fallback. UID, GID, mode and xattrs/ACLs are checked, and unsupported metadata is refused, but checks race noncooperating writers and timestamps, hard-link relationships, filesystem flags, and all possible metadata are not preserved. Serialization only covers processes using the same private store and local advisory lock, not separate stores, other editors or hosts. An open old descriptor may alter the retained inode at any time, including during or after a read; intermediate versions and sync updates can be lost. Point-in-time reinspection and fsync are best effort, not a distributed CAS or a power-failure proof. Actual sync, power loss, quota exhaustion, all metadata classes, and deployed filesystem behavior remain untested. Do not enable on real reports pending independent review and the branch dossier's remaining gates.

## Limitations

The data directory is assumed trusted against hostile local processes actively replacing directories or SQLite/WAL paths concurrently. Ordinary symlinks are refused, and report and observation content opens use component-wise `O_NOFOLLOW`; SQLite's pathname open cannot guarantee containment against an adversarial concurrent filesystem swap. Do not point this server at a tree writable by untrusted users. Non-SQLite source reads are bounded at 5 MB; SQLite rows and report listing are not paginated. Unexpected/incompatible schemas return unknown and warnings rather than invented records. Coverage writes, report edits, MapStore application-behavior indexes and static-source coverage are deferred.
