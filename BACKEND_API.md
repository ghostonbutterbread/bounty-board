# Bounty Board backend contract

## Run and security boundary

`python3 app.py [--config board.json|board.toml] [--root /absolute/path/to/Shared] [--port 9001] [--tailnet-host node.tailnet.ts.net] [--bbh /absolute/path/to/bbh] [--accept-uncoordinated-writes]` requires Python 3.11+ and uses only the standard library. Config is a JSON object or TOML top-level table with optional `root` (string), `port` (integer 1–65535), and `tailnet_host` (canonical lowercase `node.tailnet.ts.net` DNS name). Relative config roots are relative to the config file; CLI values override file values. Defaults are `~/Shared`, port 9001, and no tailnet host. Invalid files, keys or values fail startup. The root is the **parent** containing `web_bounty/` and/or `binaries/`. Metadata writes require both `--bbh` and the separate command-line acknowledgement `--accept-uncoordinated-writes`; either alone leaves them disabled. Neither can be supplied in config. Acknowledgement accepts lost-update risk, not a guarantee of safe writes.

The backend binds IPv4 `127.0.0.1` only; it has no remote-listen option, authentication, TLS or CORS. By default it accepts only `Host: 127.0.0.1:<port>` or `localhost:<port>`. Explicit tailnet opt-in additionally accepts the exact hostname with no port or `:443` and, when present, the browser-serialized `Origin: https://<hostname>` (default HTTPS port omitted); local origins must exactly equal `http://<host>`. One Host is required, and duplicate Host, Origin, or Sec-Fetch-Site headers are rejected. GET permits absent, `none` or `same-origin` Fetch Metadata; other values, including `same-site` and `cross-site`, are refused. Origin is optional for GET, mandatory for PATCH. There is no wildcard and no trust in forwarded headers. These checks are defense in depth against browser cross-origin access, **not authentication**; non-browser clients can forge them. Other local processes can read the server.

For an explicitly configured deployment, Tailscale Serve terminates HTTPS and enforces tailnet network policy; any permitted tailnet device can read sensitive API output. First review policy, DNS/certificates and existing Serve routes; then, for example, `tailscale serve --bg --https=443 http://127.0.0.1:9001`. This changes Serve configuration; do not use Funnel or public exposure. Run without writer flags for read-only operation; report writes remain disabled. Localhost HTTP and tailnet HTTPS are separate browser-storage origins, including drafts and preferences. API output can contain sensitive program names, findings, report text, URLs and evidence references; do not publish or log it. API responses include `Cache-Control: no-store`; successful static asset responses do not. Requests are not logged by the server.

The server serves `static/index.html` at `/`, and other files under `static/` at their corresponding URL paths. Filesystem paths, including symlinks, are not exposed through this static route. The HTTP server operates against live sources, not a globally atomic portfolio snapshot. Refresh to see external changes.

## `GET /api/data`

JSON shape (all collections are lane-scoped). This is an asynchronous API contract: the first request starts discovery and can return HTTP 202 with only `portfolio` and `capabilities`, with no `programs` field. Poll `GET /api/data` until a snapshot is available; do not interpret its absence as an empty portfolio. HTTP 503 means the initial scan failed and no snapshot is available. Existing clients that assumed every response was an immediately complete 200 must be updated.

Once a snapshot exists, HTTP 200 returns the existing fields plus `portfolio: {state, updated_at, error}`. States are `loading` (no snapshot), `refreshing` (previous snapshot retained), `ready`, and `error` (a scan failed or discovery was unavailable/incomplete). `updated_at` is the UTC completion time of the displayed snapshot, not a filesystem revision. An error can accompany the last snapshot; treat it as stale. First scans with incomplete discovery retain warnings and explicitly indicate error. Lane-level missing or partial sources remain indicated by their existing nulls and warnings.

A trusted `GET /api/data` with `X-Portfolio-Refresh: 1` starts an actual new scan if idle, or joins the one in progress. Ordinary GETs do not periodically rescan. Multiple clients of one server share one worker and one snapshot; a metadata write attempt invalidates the cache and schedules a scan, discarding a scan that began before the write. An indefinitely blocked filesystem can leave that single worker running indefinitely: no request timeout terminates kernel I/O, and no overlapping replacement scans are launched. A process restart resets the in-memory cache. Discovery is not a globally atomic view, and timestamps do not prove the underlying files have not since changed.

Completed snapshot example:

```json
{"programs":[{"id":"web_bounty/example","name":"example","family":"web_bounty","lanes":[{"name":"web","findings":[],"coverage":{"counts":{},"items":[],"total":0,"mapped_kinds":{},"unclassified_surfaces":0},"map":[],"gadgets":[],"reports":[],"warnings":[]}]}],"warnings":[]}
```

This is a structural example only, not a claim that an empty or missing source is complete. Discovery accepts `web_bounty/{program}/{web|api}` and `binaries/{program}/{apk|exe|mac}`, skips underscore-prefixed program housekeeping and symlinked family/program/lane directories. Program ID is `family/name`; lane name is the directory name. Other directories are not inferred to be programs/lanes.

* `root_identity`: lowercase SHA-256 hex of the canonical resolved root path, or `null` if the root is unavailable. Equivalent symlink/relative paths resolve to the same identity; different canonical paths get different identities. This is a stable namespace, not a secret: guessed paths can be hashed and compared. It contains no raw path or report content. Moving or renaming a root changes its identity. The root must remain stable while the server handles requests; this is not a snapshot or protection against concurrent filesystem replacement.
* `source_token`: an opaque random value assigned to each successful scan, distinct from `root_identity` and tied in memory to that scan's resolved path and directory device/inode. A retained token in a `refreshing` or `error` response is stale and does not authorize actions. A later successful scan receives a new token, even at the same path. The token is not a filesystem snapshot or authentication credential.
* `findings`: list from `ledgers/ledger.json` `findings`, or `null` if missing, malformed, unreadable, or over 5 MB. Each object selects `fid`, `type`, `title`, `class_name`, `severity`, `severity_rationale`, `status`, `current`, `review_tier`, `submission`, `submission_status`, `platform_outcome`, `file`, `report_dir`, `report_path`, and `evidence_path`; absent values are `null`, except that `title` falls back to recorded `type`. `status` uses the non-empty top-level field first, then `current.status`; the original `current` is also preserved, so conflicting source fields remain visible. `file` is the affected source/asset, not a report; the report fields are recorded filesystem references and may be absolute. The BBH submission object, where present, has distinct `state`, `result`, and optional `report`; do not infer submission or duplicate outcome from finding status, severity, a draft, or file names. Except for the status fallback, fields are displayed as recorded.
* `coverage`: live `ledgers/surface_coverage.sqlite`, or `null` on missing/unavailable/unsupported DB. `items` contains joined surface/class assessments: `surface_id`, `kind`, `host`, `surface_key`, `input_key`, `consumer`, `fingerprint`, `run_id`, `class_name`, `status`, `pressure`, `reason`, `boundary`, `axes`, `evidence_refs`, `reopen_when`, `assessed_fingerprint`, and `prior_status` when stale. The BBH legacy `untested` and `exhausted` statuses are shown as `no_assessment` and `bounded_review`; fingerprint/run mismatches become `stale`. `counts` count these questions, `total` is their sum, `mapped_kinds` counts mapped surfaces, and `unclassified_surfaces` counts mapped surfaces with no assessment question. Missing/empty coverage is not evidence of exhaustive mapping. SQLite opens with `mode=ro`, **not** `immutable`, so committed WAL transactions remain visible; SQLite's normal read-only WAL shared-memory coordination applies. The static source-file `coverage.json` is intentionally not conflated with live coverage.
* `map`: list from `recon/maps/map.jsonl`, with `title`, `url`, `surface`, `scope`, `status`, `path`, `tags`, `timestamp`; `null` means missing/invalid/unavailable or over 5 MB. `gadgets` is the subset whose tags contain `gadget`, including residual and archived observations; it is not a list of confirmed exploits. MapStore application-behavior indexes and observation bodies are not currently loaded.
* `reports`: list of `{path,name,kind,owner_fids,editable}` for Markdown files recursively under `reports/`, with `path` relative to that directory. `registered_report` means an exact path matches a ledger `report_path`; `generated_evidence` matches `evidence_path`; `generated_navigation`/`generated_report` are identified by BBH markers. Otherwise it is `unregistered`, or `unknown` when the ledger is unavailable or the content cannot be read, decoded or is over 5 MB. Exact ledger ownership still identifies registered reports/evidence even if content is unavailable. A content failure adds lane warning `report_content_unavailable_or_invalid`. Owners come only from exact recorded paths; basenames are never joined. `owner_fids` may have multiple entries and is empty for unregistered/unknown paths. All entries say `editable:false`. Symlink files and directories are skipped. `null` means the directory is missing or unusable; warnings signal a partial directory traversal. Content is loaded separately.
* `warnings`: strings describing missing or unavailable sources. Top-level `root_unavailable` and `discovery_incomplete` distinguish an unavailable/partially read tree from an authoritative empty portfolio. Lane warnings include `ledger_missing`, `map_missing`, `coverage_missing`, `reports_missing`, and corresponding `*_unavailable_or_invalid`. `null` means unknown/unavailable, never zero.

`capabilities` explicitly advertises `finding_metadata` (boolean), `finding_fields` and `finding_options` (severity/status lists), plus `report_edit:false`. `finding_metadata_warning` is always a human-readable warning that uncoordinated metadata writes can overwrite concurrent edits, including other hosts and sync clients, and that no shared compare-and-swap exists. Without acknowledgement, `finding_metadata` is false, fields/options are empty, the writer is not probed or invoked, and PATCH is disabled. Missing or failing BBH also disables metadata writing without disabling reads. This server has no independent record store, fabricated metrics, submission inference, search indexing, or current-agent activity.

## `PATCH /api/finding`

Enabled only with both a functioning, explicitly selected `--bbh` executable and `--accept-uncoordinated-writes`. Example body:

```json
{"family":"web_bounty","program":"example","lane":"web","fid":"D01","patch":{"severity":"HIGH","class_name":"ssrf","status":"dormant","severity_rationale":"Verified boundary"}}
```

Only the four shown patch fields are accepted; patch is nonempty and all values are strings of at most 4000 characters. Severity and status must match advertised options exactly; `class_name` matches `[a-z0-9][a-z0-9_.-]{0,99}`. FIDs match `[A-Za-z][0-9]{2,}` and must exactly match one unique, case-insensitively unambiguous ledger FID. Program names match `[A-Za-z0-9][A-Za-z0-9._-]*` and must name the existing lane. This narrower write contract does not hide other records in reads. Submission/result are not editable here; BBH's separate `--set-submission` owns that workflow.

Requires exactly one trusted `Host` (loopback or the explicitly enabled tailnet host), matching `Origin`, `Content-Type: application/json`, `X-Requested-With: Bounty-Board`, no transfer encoding, and absent or `same-origin` Fetch Metadata. Duplicate Host, Origin and Fetch Metadata headers are rejected. This protects against browser cross-origin requests and DNS rebinding, **not other local processes or permitted tailnet clients**. Body limit is 16 KiB. Filesystem preflight rejects unsafe links in BBH output/layout paths, but the data tree must be trusted against concurrent hostile local replacement.

On this incomplete branch PATCH also requires exactly one `X-Portfolio-Source` matching the latest ready scan's `source_token`; missing, stale, duplicate, or unverified source returns `409 source_unverified`. Admission excludes cache scans and other writers, and checks the configured root's resolved path and device/inode before invoking the writer and after it returns. A rejected post-write check means the update may already have happened. These checks are not atomic against hostile filesystem swaps, including A→B→A between checks. **Keep metadata writes disabled: response races and required regression coverage remain unresolved.**

The server invokes the configured BBH `agents/manual_hunter.py` with explicit family, lane, root, exact FID and temporary JSON patch, never through a shell. The BBH writer uses `EVIDENCE_ONLY`, refreshes generated navigation/indexes and may create/update context files; it does not regenerate finalized report content. The server rereads the ledger and verifies all requested values (including `current.status` if present) before returning `200 {"finding":...}`. It does not directly edit the ledger. A BBH failure or post-write verification failure disables writes for this server process; restart only after diagnosing. Failures after invocation may be partial: refresh the source before retrying. `400 invalid_finding_patch`, `403 untrusted_origin`, `404 finding_not_found`, `409 unsafe_writer_tree`, `502 writer_failed`/`verification_failed`, and `503 writer_unavailable` are possible.

There is no revision precondition or shared atomic compare-and-swap across server requests, hosts, sync clients, BBH, or other editors; concurrent edits can overwrite each other. Do not treat any local advisory lock as coordination of remote-synced writers. Stop other writers, including sync activity, and refresh before editing; even then the operator accepts the residual risk. The startup `--help` probe detects basic runtime availability, not full compatibility, and successful read-back is a point-in-time observation, not an ongoing lock.

## `GET /api/report?family=web_bounty&program=example&lane=web&path=raw%2Fexample.md`

On this incomplete feature branch, report GET requires exactly one `X-Portfolio-Source` equal to the displayed ready snapshot's `source_token`. The server requires a completed idle successful scan, checks the current resolved root path and directory identity against that scan before and after reading, and returns `409 {"error":"source_unverified"}` on a failed check. This is a breaking change. These are point-in-time checks, not exclusion of concurrent filesystem replacement; the root must still be trusted and stable. The branch is not ready for integration.

On success: JSON `{ "content": "<UTF-8 Markdown>", "revision": "<sha256 hex of exact file bytes>", "editable": false }` and HTTP `ETag: "<same sha256 hex>"`. Treat revision as opaque. The path is relative to the selected lane's `reports/`, must name an existing `.md` file, and all components are opened without following symlinks. Traversal, absolute paths, symlinks, malformed/non-UTF-8/oversized files, and unavailable paths return `404 {"error":"report_not_found_or_unavailable"}`. Bytes are limited to 5 MB. Refresh this endpoint to observe an external edit; revisions are content hashes, not locks.

All `PUT`, `POST` and `DELETE` requests, and `PATCH` requests other than `/api/finding`, return `403 {"error":"editing_disabled","message":"Report writes are disabled; retain your draft."}`. This applies to matching and stale report revisions alike; there is currently **no** conflict-checking report-write endpoint, no server-side autosave, and no claim of `409` conflict detection for reports. Preserve drafts client-side and visibly label them unsaved. A revision check followed by atomic rename is not a compare-and-swap: an uncoordinated BBH/editor/sync writer can change the file in between. Safe autosave requires a proven shared lock/versioned compare-and-swap protocol followed by every actual writer, or another owner-provided atomic conditional-write API. A lock used only by this server would not meet that requirement.

## Limitations

The data directory is assumed trusted against hostile local processes actively replacing directories or SQLite/WAL paths concurrently. Ordinary symlinks are refused, and report content opens use component-wise `O_NOFOLLOW`; SQLite's pathname open cannot guarantee containment against an adversarial concurrent filesystem swap. Do not point this server at a tree writable by untrusted users. Non-SQLite source reads are bounded at 5 MB; SQLite rows and report listing are not paginated. Unexpected/incompatible schemas return unknown and warnings rather than invented records. Coverage writes, report edits, MapStore body retrieval and static-source coverage are deferred.
