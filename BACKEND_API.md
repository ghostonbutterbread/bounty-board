# Bounty Board backend contract

## Run and security boundary

`python3 app.py [--config board.json|board.toml] [--root /absolute/path/to/Shared] [--port 9001] [--tailnet-host node.tailnet.ts.net] [--bbh /absolute/path/to/bbh] [--accept-uncoordinated-writes]` requires Python 3.11+ and uses only the standard library. Config is a JSON object or TOML top-level table with optional `root` (string), `port` (integer 1–65535), and `tailnet_host` (canonical lowercase `node.tailnet.ts.net` DNS name). Relative config roots are relative to the config file; CLI values override file values. Defaults are `~/Shared`, port 9001, and no tailnet host. Invalid files, keys or values fail startup. The root is the **parent** containing `web_bounty/` and/or `binaries/`. Metadata writes require both `--bbh` and the separate command-line acknowledgement `--accept-uncoordinated-writes`; either alone leaves them disabled. Neither can be supplied in config. Acknowledgement accepts lost-update risk, not a guarantee of safe writes.

The backend binds IPv4 `127.0.0.1` only; it has no remote-listen option, authentication, TLS or CORS. By default it accepts only `Host: 127.0.0.1:<port>` or `localhost:<port>`. Explicit tailnet opt-in additionally accepts the exact hostname with no port or `:443` and, when present, the browser-serialized `Origin: https://<hostname>` (default HTTPS port omitted); local origins must exactly equal `http://<host>`. One Host is required, and duplicate Host, Origin, or Sec-Fetch-Site headers are rejected. GET permits absent, `none` or `same-origin` Fetch Metadata; other values, including `same-site` and `cross-site`, are refused. Origin is optional for GET, mandatory for PATCH. There is no wildcard and no trust in forwarded headers. These checks are defense in depth against browser cross-origin access, **not authentication**; non-browser clients can forge them. Other local processes can read the server.

For an explicitly configured deployment, Tailscale Serve terminates HTTPS and enforces tailnet network policy; any permitted tailnet device can read sensitive API output. First review policy, DNS/certificates and existing Serve routes; then, for example, `tailscale serve --bg --https=443 http://127.0.0.1:9001`. This changes Serve configuration; do not use Funnel or public exposure. Run without writer flags for read-only operation; report writes remain disabled. Localhost HTTP and tailnet HTTPS are separate browser-storage origins, including drafts and preferences. API output can contain sensitive program names, findings, report text, URLs and evidence references; do not publish or log it. API responses include `Cache-Control: no-store`; successful static asset responses do not. Requests are not logged by the server.

The server serves `static/index.html` at `/`, and other files under `static/` at their corresponding URL paths. Filesystem paths, including symlinks, are not exposed through this static route. The HTTP server operates against live sources, not a globally atomic portfolio snapshot. Refresh to see external changes.

## `GET /api/data`

JSON shape (all collections are lane-scoped):

```json
{"programs":[{"id":"web_bounty/example","name":"example","family":"web_bounty","lanes":[{"name":"web","findings":[],"coverage":{"counts":{},"items":[],"total":0,"mapped_kinds":{},"unclassified_surfaces":0,"unassessed_surfaces":[]},"map":[],"gadgets":[],"reports":[],"warnings":[]}]}],"warnings":[]}
```

This is a structural example only, not a claim that an empty or missing source is complete. Discovery accepts `web_bounty/{program}/{web|api}` and `binaries/{program}/{apk|exe|mac}`, skips underscore-prefixed program housekeeping and symlinked family/program/lane directories. Program ID is `family/name`; lane name is the directory name. Other directories are not inferred to be programs/lanes.

* `root_identity`: lowercase SHA-256 hex of the canonical resolved root path, or `null` if the root is unavailable. Equivalent symlink/relative paths resolve to the same identity; different canonical paths get different identities. This is a stable namespace, not a secret: guessed paths can be hashed and compared. It contains no raw path or report content. Moving or renaming a root changes its identity. The root must remain stable while the server handles requests; this is not a snapshot or protection against concurrent filesystem replacement.
* `findings`: list from `ledgers/ledger.json` `findings`, or `null` if missing, malformed, unreadable, or over 5 MB. Each object selects `fid`, `type`, `title`, `class_name`, `severity`, `severity_rationale`, `status`, `current`, `review_tier`, `submission`, `submission_status`, `platform_outcome`, `file`, `report_dir`, `report_path`, and `evidence_path`; absent values are `null`, except that `title` falls back to recorded `type`. `status` uses the non-empty top-level field first, then `current.status`; the original `current` is also preserved, so conflicting source fields remain visible. `file` is the affected source/asset, not a report; the report fields are recorded filesystem references and may be absolute. The BBH submission object, where present, has distinct `state`, `result`, and optional `report`; do not infer submission or duplicate outcome from finding status, severity, a draft, or file names. Except for the status fallback, fields are displayed as recorded.
* `coverage`: live `ledgers/surface_coverage.sqlite`, or `null` on missing/unavailable/unsupported DB. `items` contains joined surface/class assessments: `surface_id`, `kind`, `host`, `surface_key`, `input_key`, `consumer`, `fingerprint`, `run_id`, `class_name`, `status`, `pressure`, `reason`, `boundary`, `axes`, `evidence_refs`, `reopen_when`, `assessed_fingerprint`, and `prior_status` when stale. `freshness` describes the fingerprint comparison: `current`, `stale`, `unknown` (either side missing), or `not_applicable` for `no_assessment`; it is not a claim that a surface is completely tested. The BBH legacy `untested` and `exhausted` statuses are shown as `no_assessment` and `bounded_review`; known fingerprint/run mismatches become `stale`. `counts` count these questions, `total` is their sum, `mapped_kinds` counts mapped surfaces, and `unclassified_surfaces` counts mapped surfaces with no assessment question. `unassessed_surfaces` lists those surfaces' identities and metadata; unlike `no_assessment`, they have no assessment row. All are read in the same SQLite snapshot. Missing/empty coverage is not evidence of exhaustive mapping. SQLite opens with `mode=ro`, **not** `immutable`, so committed WAL transactions remain visible; SQLite's normal read-only WAL shared-memory coordination applies. The static source-file `coverage.json` is intentionally not conflated with live coverage.
* `map`: list from `recon/maps/map.jsonl`, with `title`, `url`, `surface`, `scope`, `status`, `path`, `tags`, `timestamp`; `null` means missing/invalid/unavailable or over 5 MB. `gadgets` is the subset whose tags contain `gadget`, including residual and archived observations; it is not a list of confirmed exploits. Observation bodies are not included in this response; they are loaded on demand. Application-behavior indexes are not loaded.
* `reports`: list of `{path,name,kind,owner_fids,editable}` for Markdown files recursively under `reports/`, with `path` relative to that directory. `registered_report` means an exact path matches a ledger `report_path`; `generated_evidence` matches `evidence_path`; `generated_navigation`/`generated_report` are identified by BBH markers. Otherwise it is `unregistered`, or `unknown` when the ledger is unavailable or the content cannot be read, decoded or is over 5 MB. Exact ledger ownership still identifies registered reports/evidence even if content is unavailable. A content failure adds lane warning `report_content_unavailable_or_invalid`. Owners come only from exact recorded paths; basenames are never joined. `owner_fids` may have multiple entries and is empty for unregistered/unknown paths. All entries say `editable:false`. Symlink files and directories are skipped. `null` means the directory is missing or unusable; warnings signal a partial directory traversal. Content is loaded separately.
* `warnings`: strings describing missing or unavailable sources. Top-level `root_unavailable` and `discovery_incomplete` distinguish an unavailable/partially read tree from an authoritative empty portfolio. Lane warnings include `ledger_missing`, `map_missing`, `coverage_missing`, `reports_missing`, and corresponding `*_unavailable_or_invalid`. `null` means unknown/unavailable, never zero.

Dashboard submission aggregates count each finding at most once per field: nonempty `submission.state`/`submission.result` take precedence; otherwise `submission_status`/`platform_outcome` are used respectively. Missing values are not inferred from finding status. Dashboard filters scope all aggregates to the selected program or all programs; incomplete source collections are labeled and totals shown as unknown. Dashboard and workspace program selectors display the full program ID, including its family.

SQLite kind values are grouped under their JSON object-name spelling in `mapped_kinds`: strings retain their text, while numeric and null values use their JSON spelling. Groups with the same spelling are summed (for example, integer `1` and text `"1"` share one count), so counts are retained but the original SQLite types cannot be recovered from this aggregate. Excessively nested MapStore or assessment JSON that the runtime cannot decode or encode is unavailable at its own source boundary, with the normal lane warning; other sources and lanes remain readable.

`capabilities` explicitly advertises `finding_metadata` (boolean), `finding_fields` and `finding_options` (severity/status lists), plus `report_edit:false`. `finding_metadata_warning` is always a human-readable warning that uncoordinated metadata writes can overwrite concurrent edits, including other hosts and sync clients, and that no shared compare-and-swap exists. Without acknowledgement, `finding_metadata` is false, fields/options are empty, the writer is not probed or invoked, and PATCH is disabled. Missing or failing BBH also disables metadata writing without disabling reads. This server has no independent record store, fabricated metrics, submission inference, search indexing, or current-agent activity.

## `GET /api/map-observation?family=web_bounty&program=example&lane=web&path=_app%2Fexample%2Findex.md`

This read-only endpoint re-reads the selected lane's current `recon/maps/map.jsonl` and requires exactly one entry with an exact relative `path` match. All four query selectors must occur once. The selected index and body are opened componentwise without following symlinks, bounded at 5 MB each, and must be regular files containing UTF-8. The body path must end in `index.md` and cannot contain empty, dot, traversal or absolute components. An invalid, unavailable or ambiguous index, unindexed or unsafe path, missing body, wrong lane, bad UTF-8 or oversized file returns `404 {"error":"observation_not_found_or_unavailable"}` with no filesystem path. Success returns `200 {"content":"<exact UTF-8 text>"}`. The current index and body are not an atomic snapshot against concurrent writers. The interface displays body text inertly, not as rendered HTML or links; it makes no inference about free-form capability fields or whether a gadget is confirmed.

## `PATCH /api/finding`

Enabled only with both a functioning, explicitly selected `--bbh` executable and `--accept-uncoordinated-writes`. Example body:

```json
{"family":"web_bounty","program":"example","lane":"web","fid":"D01","patch":{"severity":"HIGH","class_name":"ssrf","status":"dormant","severity_rationale":"Verified boundary"}}
```

Only the four shown patch fields are accepted; patch is nonempty and all values are strings of at most 4000 characters. Severity and status must match advertised options exactly; `class_name` matches `[a-z0-9][a-z0-9_.-]{0,99}`. FIDs match `[A-Za-z][0-9]{2,}` and must exactly match one unique, case-insensitively unambiguous ledger FID. Program names match `[A-Za-z0-9][A-Za-z0-9._-]*` and must name the existing lane. This narrower write contract does not hide other records in reads. Submission/result are not editable here; BBH's separate `--set-submission` owns that workflow.

Requires exactly one trusted `Host` (loopback or the explicitly enabled tailnet host), matching `Origin`, `Content-Type: application/json`, `X-Requested-With: Bounty-Board`, no transfer encoding, and absent or `same-origin` Fetch Metadata. Duplicate Host, Origin and Fetch Metadata headers are rejected. This protects against browser cross-origin requests and DNS rebinding, **not other local processes or permitted tailnet clients**. Body limit is 16 KiB. Filesystem preflight rejects unsafe links in BBH output/layout paths, but the data tree must be trusted against concurrent hostile local replacement.

The server invokes the configured BBH `agents/manual_hunter.py` with explicit family, lane, root, exact FID and temporary JSON patch, never through a shell. The BBH writer uses `EVIDENCE_ONLY`, refreshes generated navigation/indexes and may create/update context files; it does not regenerate finalized report content. The server rereads the ledger and verifies all requested values (including `current.status` if present) before returning `200 {"finding":...}`. It does not directly edit the ledger. A BBH failure or post-write verification failure disables writes for this server process; restart only after diagnosing. Failures after invocation may be partial: refresh the source before retrying. `400 invalid_finding_patch`, `403 untrusted_origin`, `404 finding_not_found`, `409 unsafe_writer_tree`, `502 writer_failed`/`verification_failed`, and `503 writer_unavailable` are possible.

There is no revision precondition or shared atomic compare-and-swap across server requests, hosts, sync clients, BBH, or other editors; concurrent edits can overwrite each other. Do not treat any local advisory lock as coordination of remote-synced writers. Stop other writers, including sync activity, and refresh before editing; even then the operator accepts the residual risk. The startup `--help` probe detects basic runtime availability, not full compatibility, and successful read-back is a point-in-time observation, not an ongoing lock.

## `GET /api/report?family=web_bounty&program=example&lane=web&path=raw%2Fexample.md`

On success: JSON `{ "content": "<UTF-8 Markdown>", "revision": "<sha256 hex of exact file bytes>", "editable": false }` and HTTP `ETag: "<same sha256 hex>"`. Treat revision as opaque. The path is relative to the selected lane's `reports/`, must name an existing `.md` file, and all components are opened without following symlinks. Traversal, absolute paths, symlinks, malformed/non-UTF-8/oversized files, and unavailable paths return `404 {"error":"report_not_found_or_unavailable"}`. Bytes are limited to 5 MB. Refresh this endpoint to observe an external edit; revisions are content hashes, not locks.

Other than the opt-in collaboration endpoint below, report-edit requests are disabled. The ordinary report endpoint remains read-only.

## Experimental collaboration source autosave (default off)

This branch is a **synthetic-tested prototype, not approved for real deployment**. `--collaboration-dir PRIVATE --report-autosave` enables synchronous publication on accepted collaboration POSTs; the switches are not configuration-file options. `--experimental-fixture-publish` is separate and mutually exclusive. The private store and source must be on the same filesystem. `GET /api/data` advertises `capabilities.report_autosave`.

A normal `POST /api/collaboration` with `base`, `content`, and unique `request_id` first commits the submitted version to the private SQLite store and performs the existing three-way merge against the observed source. When autosave is enabled the JSON includes `store_saved: true` and `publication.state`: `published`, `conflict`, or `outcome_uncertain`. `published` means exchange, directory fsync and current inode/content inspection succeeded; it is not a guarantee that external editors, older open descriptors, or sync will not change the file later. `conflict` can mean a collision detected **after** a visible exchange: never imply that the file was untouched. An `operation` is an opaque recovery handle when an operation was created. An unresolved store conflict prevents publication. The store may be saved even if publication or observation fails; retain the request ID and local draft. The call is synchronous: no `pending` receipt is currently supplied. Network failure is not confirmation of either store or file save.

`GET /api/collaboration/recovery` with the normal report identity and `request_id` returns the current store version, original `store_receipt`, and a fresh `publication` inspection; it never republishes. Unknown request IDs return 404. An interrupted publication attempt is `outcome_uncertain`; do not retry with a new ID blindly. If a stored request has no publication attempt, recovery reports `conflict`/`not_published` (or `outcome_uncertain` while retained reconciliation is incomplete). Exact POST retry uses the store's original receipt, reports a fresh publication assessment, and never initiates an exchange for a previously stored request. Stop and retain the private operation for manual review when uncertain.

With autosave enabled, ordinary collaboration GETs, POSTs, history and recovery inspect retained operations in creation order and record newly observed snapshots in history. Successful responses include `reconciliation: {state: "complete"|"backlog"|"uncertain", scanned: N}`. A sweep examines at most 64 operations per interaction; a backlog advances on subsequent interactions, and POST returns HTTP 503 `retained_scan_backlog` without accepting the submission until its sweep completes. A sweep that finds an incomplete or uncertain publication reports `uncertain` and prevents further automatic exchanges, even when the new draft is saved to the store. Progress is per server and resets on restart; a multi-request sweep is not an atomic snapshot. If scanning fails, HTTP 503 `retained_reconciliation_unavailable` means retain the local draft and retry. Observed identical consecutive snapshots do not duplicate events; intervening versions may be missed. If a retained edit conflicts or leaves the store head different from the visible source, publication is reported as `conflict` and no automatic follow-up exchange is performed. The store receipt's content remains the original request result; use a fresh GET for the current reconciled head. For a divergent shared head, the UI offers a preview of both the current Markdown snapshot and the merged shared report, then a separate **Save merged report** action. Conflict resolution first saves to the shared store only, requiring that separate preview and confirmation when publication is still needed. `GET /api/collaboration` supplies `source_snapshot` when the source is present. An explicit POST uses `{ "action": "reconcile", "base": <expected shared revision>, "content": <exact shared text>, "source_snapshot": <exact observed Markdown>, "request_id": <new unique ID> }`. The server rejects stale snapshots, changed heads, unresolved conflicts and incomplete/uncertain scans. Its stored receipt binds the source snapshot too; exact retries never perform another exchange. On `reconciliation_changed`, refresh and review; an ambiguous network outcome instead requires original-request inspection. If a sweep spans multiple requests, its completed result can be consumed once by the next explicit reconcile after checking that no new publication operation was added; a later scan can still discover old-descriptor edits made after their earlier observation. This is not a CAS.

Each operation retains a separate board copy, the initially observed inode, and the exchanged-out inode, in owner-only private storage. This content is plaintext, unbounded, and has no automatic cleanup. Linux `renameat2(RENAME_EXCHANGE)` is required; unsupported/cross-filesystem cases fail without ordinary-rename fallback. UID, GID, mode and xattrs/ACLs are checked, and unsupported metadata is refused, but checks race noncooperating writers and timestamps, hard-link relationships, filesystem flags, and all possible metadata are not preserved. Serialization only covers processes using the same private store and local advisory lock, not separate stores, other editors or hosts. An open old descriptor may alter the retained inode at any time, including during or after a read; intermediate versions and sync updates can be lost. Point-in-time reinspection and fsync are best effort, not a distributed CAS or a power-failure proof. Actual sync, power loss, quota exhaustion, all metadata classes, and deployed filesystem behavior remain untested. Do not enable on real reports pending independent review and the branch dossier's remaining gates.

## Limitations

The data directory is assumed trusted against hostile local processes actively replacing directories or SQLite/WAL paths concurrently. Ordinary symlinks are refused, and report and observation content opens use component-wise `O_NOFOLLOW`; SQLite's pathname open cannot guarantee containment against an adversarial concurrent filesystem swap. Do not point this server at a tree writable by untrusted users. Non-SQLite source reads are bounded at 5 MB; SQLite rows and report listing are not paginated. Unexpected/incompatible schemas return unknown and warnings rather than invented records. Coverage writes, report edits, MapStore application-behavior indexes and static-source coverage are deferred.
