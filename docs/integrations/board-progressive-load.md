## Evidence

- The actual beta browser/backend is blocked by a deterministic report-read barrier: `static/tests/progressive-load.synthetic.test.cjs` starts `tests/progressive_browser_fixture.py`, opens the actual UI with real Chromium and verifies the loading state. It reaches the held `reports/example.md` read, then the portfolio heading times out while the release marker is absent. The test releases the barrier and terminates the synthetic server in `finally`. This is an **expected failing test**, not a passed feature. It is not included in the default `npm test` command.
- `tests/test_progressive_phase_experiment.py` is an isolated single-thread experiment, not an implementation: it temporarily replaces the process-global `reports` function to establish that the current ledger and other projections can be obtained without any report reads. For 25 synthetic reports with an injected 5ms per-read delay, the observed no-report projection took 0.0239s and full discovery 0.1557s. The final read correctly returned 25 reports and retained the registered finding owner. These are fixture measurements, not production latency or a promise. A process-global monkeypatch is unsafe in the threaded HTTP server and must never be adopted as the solution.
- Both checks ran only in disposable nonroot, `--network none`, read-only-source containers with writable `/runboard` tmpfs, isolated HOME/TMPDIR/XDG, no real data, and no live Bounty Board request. Browser test preflight confirmed loopback bind and external network error 101; the Chrome process used `--disable-dev-shm-usage`. Browser test used the local Chrome and Playwright distributions and host library directory mounted read-only. No host `/tmp` or host `/dev/shm` was used. The first two browser setup attempts failed (host-library/loader mismatch, then ICU resolution); mounting the matching host library directory at its original path resolved both; the final failure was the intended portfolio assertion, not a launch failure.

## Exact blocker and resume point

A safe implementation needs an explicit generation/identity protocol and a merge policy, not just a background call to the existing `discover`. `discover` currently mixes ledger, map, WAL-aware SQLite and report reads; report ownership depends on the same lane's findings. `/api/data` derives root identity only after the scan; a symlink/root change during a blocked scan can otherwise associate old contents with a new identity. `load()` replaces `state.data`, normalizes selection and rerenders the application; blindly applying a late full snapshot can undo newer metadata, replace a live report editor or destroy focus, and leak stale capabilities or report paths into actions. HTTP is threaded, so unbounded refreshes could create unbounded blocked readers unless work and lifecycle are explicitly bounded. Write-enabled source autosave, collaboration, and metadata modes must remain functional under their existing trust checks.

Resume by designing the narrowest read-only phased API, with server-owned generation/root identity checked before and after work, a serialized/bounded report scan, explicit loading versus unavailable states, and late publication that cannot authorize stale actions. Specify how refresh/root changes invalidate work and how shutdown handles an I/O operation that does not return; do not assume Python can cancel a thread blocked in filesystem I/O. Merge only report projections for the matching generation into still-current data, and update visible UI without replacing a focused editor or unsent drafts. Retain the synchronous existing path for opted-in write modes if this is needed to preserve semantics; do not disable those modes. Independently review the final design and combined diff with the concurrently owned warning UI changes.
