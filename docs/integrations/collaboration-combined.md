## Combined behavior and repairs

The real Python API returns a bounded recent 50 metadata events, cursor pages and report-scoped on-demand versions; the browser uses these, persists the exact pending request, and uses Web Locks to separate live tab namespaces. The new `static/tests/collaboration-combined.synthetic.test.cjs` drives real Chromium and the real loopback Python server: it creates over 50 events, holds the real older-page response while another HTTP edit commits and the browser polls, checks continuity, fetches the old conflict's input and resulting head on demand, resolves it by ID, verifies the server metadata and confirms the synthetic source remains unchanged. Other real-backend browser tests cover exact pending replay after a lost acknowledgment, newer edits, multiple tabs, offline retries and stale-resolution recovery; the existing fake-adapter metadata test is not counted as real-backend coverage.

Three integration defects were reproduced before fixes:

1. The recent-page boundary disappeared if polling advanced while an older page was still in flight. The browser now retains its current boundary before awaiting that page. `combined-red-1.log` failed the specific missing-boundary assertion; `combined-green-1.log` passed after repair.
2. A successfully resolved old conflict stayed displayed as unresolved because only the newest page is refreshed. `combined-red-3.log` verified HTTP 200 and the server's resolved metadata, then timed out on the stale UI. A successful local resolution now updates cached metadata in all three displayed/cached collections. This does **not** refresh an old cached conflict resolved by another tab; see open gates below.
3. Fixture publish could be rejected locally because a background poll was busy even though the visible status still said ready. `publish-red.log` deterministically held a real poll and observed no publish POST; `publish-green.log` passed after queuing the single explicit action behind that poll, with no publish when the poll fails, a local draft exists, or the shared revision changed. These are fixture-only semantics, not a production publishing safety guarantee.

## Remaining review and safety gates

- The old-paged-metadata cache can still show an obsolete unresolved state when **another** tab resolves an event outside the current 50; the server rejects a second resolution and the frontend preserves the draft, but fresh old-page status needs a concrete cross-tab regression and refresh design. Likewise, if more than one complete recent page arrives between polls, an uncached interval may be skipped after paging; the new test proves continuity for a single incoming event during an in-flight page, not arbitrary bursts. Investigate both before claiming complete history continuity or cross-tab freshness.
- No crash/power-loss, actual filesystem exhaustion, storage quota-clearing, cross-host, Syncthing, browser lifecycle matrix, or final-check/replace race safety proof. Fixture publication is explicitly unsafe for real reports and must remain disabled in the real service. The observation lock only coordinates cooperating servers using one trusted stable private-store directory and local reliable flock; it does not coordinate external writers or separate stores/hosts. Root inode reuse and directory replacement remain unresolved. LocalStorage and SQLite contain plaintext; browser storage can fail or be cleared; tab reload recovery depends on browser Web Locks/navigation behavior. SQLite page limits do not bound journals, other files, or total disk; no automatic retention/eviction. Paged browser metadata can grow during a session. See both child dossiers and the historical parent dossier for their detailed constraints.
