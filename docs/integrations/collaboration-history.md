## Frontend/backend contract

All three GETs require the existing exact `family`, `program`, `lane`, `path`, and `root_identity` parameters, trusted Host/Origin/Sec-Fetch-Site, a valid available report, root binding and path checks. No paths are returned. Unknown/invalid version or query is 404; unavailable storage is 503. `revision` values are lowercase SHA-256 hex.

- `GET /api/collaboration`: existing current `revision` and `content`, plus `history` (at most 50 newest events, descending event id) and integer `unresolved_count`. It observes source under the existing shared observation lock.
- `GET /api/collaboration/history[&before=<event-id>]`: `{history, next_before, unresolved_count}`; metadata-only events with exactly `id`, `kind`, `revision` (incoming/source), `base`, `head` (result), `resolved_revision` (nullable). `next_before` is the last returned id if there are older events, otherwise null. Pass it unchanged to fetch strictly older events; page order is descending. Counts represent each request's current database snapshot and may change while paging. Newer writes do not shift older cursor pages. Unresolved conflicts are not inserted separately into the current page; page to them. The events index allows cursor seeking.
- `GET /api/collaboration/version&revision=<revision>` returns `{revision, content}` for the same report only. Fetch both event `revision` and `head` (and `base` / `resolved_revision` when useful) to recover input and resulting snapshots. Content is verified against its hash. History and version GETs validate and read the source path and bind the root but deliberately do not add a source observation; this allows retained history reads when a changed source cannot be recorded because the store is full. Current GET/POST still observes the source. A missing/unavailable source still blocks these reads under the existing safety model.
- `POST /api/collaboration` keeps the previous protocol, transactional request-id result, and observation locking. Full or unavailable storage returns 503 with an instruction to retain local text and retry; `collaboration_capacity` specifically requests increasing capacity or freeing disk and retrying the **same request ID**. A source observation can independently commit before a submission fails, but the failed submission's versions, event, head, and request receipt are rolled back together. Client-local pending text remains the client's responsibility.

The frontend must fetch versions on demand and page history rather than expect `content` or `head_content` on metadata. Existing unmodified frontend is incompatible until the sibling integrates its changes. The backend no longer offers the old unbounded internal `history()` method.

## Resource and storage policy

`--collaboration-max-bytes` (or `make_server(..., collaboration_max_bytes=...)`) sets SQLite `max_page_count` per connection; default 512 MiB, minimum 65536 bytes, rounded down to the SQLite page size. This caps database pages, not total disk consumption: journal/WAL files, filesystem overhead and temporary merge files need extra free disk space. Existing oversized stores are not truncated; migration/index creation can fail if insufficient capacity. All cooperating servers on a store must use the same limit. Increasing the limit and/or freeing disk permits retry; there is no automatic eviction, compaction, retention or deletion of confirmed versions. Operators must budget and monitor storage. The inherited limit of 5,000,000 UTF-8 bytes per document and 30,050,000 bytes per POST remains; JSON escaping can enlarge the wire response. Each server admits at most four simultaneous collaboration requests before returning 503/Retry-After, and sets a 15-second socket idle timeout after route admission. This is not a global HTTP connection/header or cross-process concurrency limit and not a total request deadline.
