## Contract

Before POST, the exact request including request ID, base, content and optional conflict ID is persisted with the current editor text. An acknowledgment clears the pending payload as part of persisting the resulting state. If the editor changed meanwhile, the acknowledged input revision is the next base; the newer text is retained and sent separately. A 409 on a conflict resolution preserves the editor, and an explicit retry submits a new edit against the original conflict base (so a competing resolution is not silently overwritten). Existing conflict records can supply the original base when visible in history.

POST and initial/poll GET errors use at most three automatic attempts per run, with backoff, then expose a manual retry. The retry budget resets on reload or explicit retry. Browser storage errors and concurrent changes retain the existing copy-your-draft warning; durability is impossible when storage is unavailable, cleared or quota-exhausted. The pending body may contain sensitive text in localStorage, as does the draft; do not log it.

Polling consumes `history` metadata and scalar `unresolved_count`; an initial full 50-item page implies a possible older page, so the last ID is sent as `before`. An empty last page is valid. Explicit paging consumes `/api/collaboration/history` and `next_before`; individual input or head text is fetched from `/api/collaboration/version` on selection. Polling replaces the recent page until the user pages; after paging, the prior recent boundary is retained in memory to prevent gaps as the feed advances. That user-initiated browsing cache can grow until navigation/reload; the network pages, not total retained browser metadata, are bounded. The frontend temporarily accepts legacy full-text history entries for compatibility with the base backend, without rendering the snapshots inline. The original backend at this base does **not** implement history/version endpoints or bounded metadata; the sibling change must be integrated before claiming the new wire contract works end to end. The fake adapter test does not prove real backend integration.

A tab claims its namespace with an origin Web Lock held for the page lifetime. A normal reload can reclaim the `window.name` namespace once the old document releases its lock; if an inherited/cloned reload races a live owner, it receives a new namespace. A normal navigation (not a reload) intentionally receives a new namespace; prior localStorage records are retained but are not automatically rediscovered. In browsers without working Web Locks, each navigation uses a new namespace and the UI warns that reload recovery is unavailable. Browser session restoration or cloned reload states with no live owner, unsupported Web Locks, BFCache/navigation variations, and concurrent reload races cannot be assumed to provide stable tab identity; test the deployment browsers before activation. Existing unscoped browser-only draft handling remains separate. Browser-local storage and Web Locks are not cross-device storage or encryption.
