## Contract and operation

The Bounty Board app now has an **opt-in shared draft** path. Start an isolated server with `--root <synthetic-root> --collaboration-dir <owner-only-private-dir>`; use a Git executable for line-based three-way merging. `--collaboration-dir` is required; without it the collaboration API is disabled and the existing browser-only editor remains unchanged. Store the private database outside the source tree and synced/shared locations. It contains full sensitive report text; owner-only directory/database modes are checked, but this is neither encryption nor a sandbox. It has no retention policy.

The app observes the source on each collaborative request, preserves source/client versions in SQLite, serializes participating changes in one server's lock and database transactions, and merges nonoverlapping line edits. A conflict is retained, shown in history (including unresolved conflicts older than the latest 100 events), and can be resolved explicitly against the observed head. Resolution and request IDs are persisted transactionally. The UI polls every two seconds, autosaves a shared draft after edits, keeps tab-scoped local recovery, retries failed requests, doesn't replace edits typed while a request is in flight, and offers historical input/result selection as a new shared revision. Browser storage failure remains visible and requires copying the text. Existing browser-only drafts are not silently migrated into the collaborative namespace.

Shared draft save **does not save the report file**. A separate manual publisher is exposed only when `--experimental-fixture-publish` is explicitly specified alongside `--collaboration-dir`, an explicit `TMPDIR`, and a root resolving beneath that `TMPDIR`. This is a synthetic-fixture convenience, **not a security boundary**: an operator controls TMPDIR, and the option must never be used for real reports or the real service. It checks the expected head, refuses unresolved conflicts, observes and rechecks the source, uses a no-follow directory walk and same-directory replace, then observes the result. Local changes observed between the two source reads are recorded and block publication. A writer between the final read and replace can still be overwritten before observation. The process lock does not coordinate other Bounty Board processes, editors, BBH, Syncthing, or other hosts. It does not protect or retain unobserved variants. Do not claim compare-and-swap, cross-host safety, or Syncthing conflict retention.

The API reuses the app's exact Host/Origin and Sec-Fetch-Site restrictions; POST additionally requires a single JSON content type, same origin, and `X-Requested-With: Bounty-Board`. These checks are not authentication against local processes or a replacement for authorized Tailscale Serve. Every collaboration request binds the root identity advertised by `/api/data`; a mismatched root is rejected before observation or write. The identity hashes the canonical root path, not a filesystem generation, so replacing a directory at the same path is not detected. Report identities are validated and source paths opened without following path-component symlinks. Source deletion/unavailability stops collaboration requests rather than inventing an empty source. History polling returns recent 100 events plus all unresolved conflicts; retained older resolved history is not yet paginated through the API. History/unresolved-conflict growth and storage limits are not bounded. Git's clean line merge can still be semantically wrong.

## Evidence

All tests used disposable roots below the inherited scratch `TMPDIR`, isolated HOME and XDG config/cache/data directories, and synthetic reports. No real reports, Shared files, live service, Tailscale, or remote Syncthing were touched.

- `PYTHONPATH="$PWD" python3 -W error::ResourceWarning tests/safe_suite.py`: **53 passed**, explicitly excludes `test_backend.BackendTests.test_real_bbh_metadata_write_on_disposable_fixture`. The expected argparse rejection is emitted by an invalid-config test. This includes real HTTP tests for stale publication, idempotent retries and reused request IDs, persisted conflicts/resolution/restart, hostile Host/Origin/content type, disabled source publishing, and a deterministic synthetic file update between source observations. The last test injects ordering in-process; it is not a cross-host race proof.
- `node --test static/tests/collaboration.synthetic.test.cjs`: **1 passed**, real Chromium/Playwright pages with separate browser contexts and the actual Python HTTP server. It exercises shared autosave/live update, held *post-commit* response with a later local edit, held concurrent conflicting request, retained conflict and explicit resolution, external synthetic file change, server restart, history undo/redo, manual source publication, and a cloned popup with two separate unsent local drafts while POSTs fail. It does not test independent Syncthing or a real tailnet. The test starts a server in a child process and cleans it up.
- `npm test`: **58 passed**, excluding the package script's metadata-writer browser test by its explicit skip pattern. This includes the previously timed-out `static/tests/drafts.synthetic.test.cjs`, which passed in the fenced run; the earlier timeout was intermittent, not a proven root cause. The collaboration E2E is run separately and is not included in `npm test`.
- TDD: first API test failed for absent `collaboration_dir`, first browser test failed for absent shared UI, source-publish test failed for absent fixture publisher, deterministic source-race test failed because publication overwrote the injected edit, cloned-popup test failed because sessionStorage was cloned, and history redo test failed for absent resulting-version control. - The first complete Python suite run exposed an outdated exact `make_server` mock assertion; the test now checks the new disabled-by-default keyword arguments and the complete selected suite was rerun green. One E2E run under concurrent load attempted publication before the initiating client's save acknowledgment and timed out; the test now waits for the initiating client's ready status. A subsequent standalone run passed, but this remains an intermittent timing area worth exercising in review.

Independent review is **not performed**; the parent owns review of the complete diff, data-loss behavior, paths, security, test evidence, and integration.
