- Branch: `feat/board-bulk-actions` (worktree `bounty-board-bulk`), from the head of `feat/board-report-links-recent` (`c5cd47c`). Not pushed, not merged, not activated.
- Follow-up (orchestrator, decisions resolved): BBH delete merged to BBH beta `b3c6aced` (permanent, minimal tombstone, no restore, `--actor`); `active`/`pending-review` writable and exact previous status restorable; previous status remembered server-side; table severity as pills; submission note once per browser; Evidence link. ## What it does

Applies to the dashboard drill-down lists (severity, class and category breakdowns) and the Findings table. The look is unchanged apart from the new controls.

1. **Pills.** Clicking a severity badge in a drill-down list or the Findings table opens coloured pills in BBH order (Exceptional, Critical, High, Medium, Low, Info, Unknown), with the current value checked and focused. Every row shows its submission badge (not only "Not submitted"); clicking it opens Not submitted / Submitted / Dropped plus Valid / Duplicate, which are enabled only when the finding is Submitted. Enter or Space on the trigger opens, arrow keys move, Enter picks, Escape closes and returns focus. When the writer is off the pills are disabled and the popover says why (the table trigger is disabled). One click saves a submission state; the "records state in the ledger only" note shows once per browser inside the popover.
2. **Context menu.** Right-click a row, or press Shift+F10 / the ContextMenu key while a row's checkbox is focused. Single row: Open finding, Open finding in new tab, Go to report (or "No linked report"), Open report in new tab, Change severity…, Change class…, Submission…, Move to Gadgets…, Move to MapStore…, Copy ID, Delete…. For an archived row: Restore… and Delete permanently… instead of the edit items. Right-click on a selected row acts on the whole selection (heading "N findings selected", Copy IDs). Shift+right-click keeps the browser menu. The menu reuses the shared opaque `.menu`/`.popover`, keyboard navigation (arrows, Home/End, typeahead), Escape and Tab close it, focus goes back to the row, and it is placed inside the viewport.
3. **Multi-select.** A checkbox per row (Space toggles), Shift+click for a range (also unselects a range), Ctrl/Cmd+click on a row, "Select all N" on each expanded drill-down list and "Select all" in the Findings filter bar, Escape clears. A sticky bar shows the count and: Select all (N), Change severity, Change class, Submission, Delete, Restore / Delete permanently (for archived rows), Clear. The selection covers rows in the current list; rows that leave the view are dropped from it.
4. **Drag.** Drag a drill-down row (or the selection, if the row is selected) onto a class row (sets that class), a category row (only if every loaded finding in that category has the same raw class; otherwise the preview says why and the drop is refused) or a named severity row. A floating preview names the change and count; dropping more than one finding asks for confirmation first.
5. **Bulk writes.** One finding at a time through the existing single-finding write path, each with its own `expected_revision`: `PATCH /api/finding` for severity, class and status, `POST /api/finding/submission` for submission. A progress bar and "saving i of N" show in the selection bar. A stale finding (`finding_changed`) is reported and never overwritten; a writer failure stops the run (the server has disabled the writer) and the rest are reported as not attempted. Failed and unattempted items stay selected, then the data is refreshed once so a retry uses current revisions. Sibling revisions roll forward through the existing `BoardFindingView.rebase`. Undo (toast and bar) restores the previous values of the last change for items that still hold the value it wrote; items changed since, previous values BBH will not accept (for example a template severity), and results BBH cannot clear are skipped and listed.
6. **Delete = archive.** "Delete" sets status `archive` through the edit path after a confirm dialog that says it hides the findings from the dashboard and lists while the ledger keeps them, with Undo. Archived findings (status `archive`, or Bounty Core's `archived`) are hidden from the dashboard counts, breakdowns, drill-downs, program table and the Findings table unless "Show archived" (dashboard toolbar and Findings filter bar, remembered per browser) is on; the toggle shows "Archived N".
7. **Restore.** Pills: "Previous status" (the exact status each finding had when the Board archived it, stored by the server, so it works from any device; when nothing is stored, the finding is restored as `confirmed` and the popover and result say so) or one of the offered statuses (raw, confirmed, active, pending-review, dormant, novel, complete). Undo after Delete writes back the exact previous status too.
8. **Delete permanently** (archived findings only, single or bulk, shown only when the writer advertises `delete`): one confirm dialog naming the count: "Delete permanently removes the finding(s) and its/their generated report files. It cannot be undone." and "Archive is how to keep something recoverable." A finding marked `archived` is first set to `archive` through the edit path, then deleted (the dialog says so). No Undo and no restore. A BBH refusal (for example "it is the highest FID of its prefix; delete it after a newer finding exists") is shown plainly in the selection bar and the finding stays selected; BBH warnings after a delete appear in a non-blocking notice.
9. **Template placeholders.** Rows whose severity is a schema example such as `LOW|MEDIUM|HIGH|CRITICAL` (taxonomy kind `placeholder`, or a pipe list of three or more levels) or whose title/type is `short vulnerability label` / `short novel pattern label` get a muted "Template placeholder" badge; the raw severity group in the dashboard breakdown is labelled the same way. Expanding that group gives "Select all N"; the Findings filter bar has "Select template placeholders (N)". So: select, Delete (archive), Show archived, select again, Delete permanently.
10. **Report markers.** Where a finding has no linked report, a muted "No report" marker (focusable, with a tooltip) says why: no `report_path` in the ledger, or a `report_path` whose file is not among the lane's reports. When an unregistered report file in the same lane (kind `unregistered`, `generated_report` or `unknown`) has the finding ID in its path as a whole token (A01 does not match A010), a "Possible report" real link opens it, labelled as unlinked. A generated evidence file with the ID in its path is linked after it as "Evidence". Nothing is written to the ledger (`report_path` is not writable). Markers appear once the lane's report index is loaded.

## Why some findings have no "Report" link

The link appears only when a registered report exists: a report file whose path the ledger records in `report_path` (the server marks it `registered_report` with the finding as owner). The orchestrator's read-only count on real data: of 259 findings, 192 link to a registered report; 65 have no `report_path` at all (60 of those have a generated evidence file and 21 an unregistered report file with the ID in its path); 2 have a `report_path` whose file does not exist. The new markers make each case visible, and "Possible report" covers the unregistered files.

## Contract

- Server (`app.py`): writer features `delete` (`--delete-finding` in `manual_hunter.py --help`) and `actor` (`--actor`); `capabilities.ledger_actions.delete = {enabled, requires_status: "archive"}`; `POST /api/finding/delete`; status tokens and `GET /api/archive-state` with the `ArchiveState` store in `--state-dir` (see `BACKEND_API.md`). Same trust checks, payload validation, `finding_precheck` (root/revision/tree), metadata lock, `run_writer` verification and disable-on-failure as the other ledger actions. Refuses `409 not_archived` before invoking BBH. Exit 1 with an unchanged ledger: `409 delete_refused` with BBH's `reason`, writer stays on. Exit 3: verified success with `warnings: true` and `warning_text`. Exit 2 or other: writer disabled. Verification: the FID is gone from the re-read ledger.
- Frontend: `static/modules/finding-actions.js|css` (new). Seams, each commented: `app.js` (`BoardUI.openPills` and `severityOptions` shared by the table and the module, the severity cell as a pill trigger that keeps `data-metadata`/`value` and saves through the existing `saveMetadata` flow (pending-value drafts, root recovery and conflicts unchanged), `isArchived`/`shownFinding`/`archiveToggle`/`pickButton` helpers, `state.showArchived`, row data attributes on drill-down `<li>`s, `data-sev` on table rows, the archive filter in `dashboard()`/`findings()`, the toggle's change handler, `ctx.reload` and `ctx.reportIdFor`), `index.html` (one module line), `ledger-actions.js` (exports its dialog shell, class combobox, `post`, `failure`, `openMoveDialog` on `BoardLedgerActions`; the one-class Reclassify review is unchanged).
- Fake writer (`tests/test_ledger_actions.py` `FAKE_WRITER`): implements `--delete-finding` per the contract (refuses unless archived, removes the entry, deletes generated report files whose lane-relative path contains the FID, appends a minimal tombstone; refusals print `[manual_hunter] ...` on stderr and exit 1; modes `delete-refuse`, `delete-highest` (the highest-FID refusal), `delete-warn` (exit 3 with a `Warning:` line), `delete-keep`, `usage` (exit 2)). The default help text is unchanged, so existing capability tests are unaffected; the new tests set `FAKE_HELP`.

## Decisions made

1. **Delete is archive in the UI.** The Board only writes through BBH. The first step is `status: archive` via `--edit-finding`; the permanent step is a separate, explicit action available only from the archive.
2. **Findings table severity is the same pills** (resolved). The trigger keeps `data-metadata="severity"`, its `value` and the `severity for <title>` label, and picks go through the existing metadata write flow, so pending values, conflicts and root recovery behave as before.
3. **Submission pills save in one click** (resolved); the ledger-only note is shown once per browser. Results are offered only for Submitted findings, and state is always sent explicitly.
4. **Previous status is remembered by the server** (resolved), in the Board's private state directory, so Restore works from any device; `confirmed` is the visible fallback.
5. **One refresh after a bulk run** (and after any run with a failure), not after a successful single pill change, which updates the row in place like today's inline edits.
6. **Selection is per list.** It survives the refresh's loading state but drops rows that leave the current view, so an action never applies to rows you cannot see.
7. **Category drops map to a raw class only when unambiguous** (exactly one raw class among loaded findings in that category).
8. Checkbox names are "Select finding <ID>", not the title, so they do not collide with filter checkbox names in existing tests.

## Gaps

- Previous status is stored only for findings the Board archived (from this follow-up on); findings archived by BBH or by hand restore as `confirmed` unless another status is picked. The store is per Board host.
- BBH cannot clear a submission result, so Undo skips items where the change added a result.
- Bulk runs are sequential BBH calls (no batch command); large selections take one BBH run per finding.
- Dropping onto a category row (and its refusal when ambiguous) is implemented but not covered by a browser test.
- The drag is mouse only; the context menu and selection bar are the keyboard path.
- Report markers use the lane's report index; in the summary phase (reports not yet loaded) no marker is shown until the complete phase.
- The table's severity pills keep the old select's error handling (banner plus pending value); dashboard and bulk changes report in the selection bar.
- Concurrency limits are those of `PATCH /api/finding`: not compare-and-swap; stop other writers and sync before editing.
- The fake writer mirrors the BBH delete contract as described in the brief; the real BBH `b3c6aced` was not run here.
