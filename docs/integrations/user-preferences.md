## Contract

- The server user's `~/.config/bountyboard/user.conf` is JSON, independent of the data root and deployment config. `make_server(..., user_config=...)` is for disposable fixtures, not a new CLI option. Missing means defaults; a failed or corrupt read refuses writes without replacing the file. Writes use a private 0600 exclusive temporary file, fsync and directory-relative atomic replacement. A 0600 advisory lock serializes cooperating Board processes; path components and the target are opened without following symlinks; paths inside the Board data root or `~/Shared` are refused.
- The index response includes a bounded preference snapshot read through that same validated store, or an error marker. JSON is ASCII-encoded and escapes `<` and `&` (including escaped U+2028/U+2029); the HTML response is `Cache-Control: no-store` and retains the existing navigation Host/Origin/Sec-Fetch and anti-framing protections. There is no synchronous XHR. The snapshot initializes server preferences and an in-memory browser fallback before deferred app initialization, including when localStorage writes fail. A bounded asynchronous read and fill-only migration follow; a failed read is retried on online/timer and its alert clears only after successful hydration. The late update avoids replacing an active report editor; Settings, sidebar, theme and untouched Recent lists receive targeted updates. GET, migration, and save operations have 3-second browser aborts.
- `GET /api/user-preferences` uses the existing Host/Origin/Sec-Fetch gate. `POST` also requires same-origin, the Board request header, JSON and a bounded body. The allowlisted API exposes only UI preference keys. It applies key patches under the lock; list fields and terminal Settings are separate keys. Conditional writes check persisted per-key revisions and reject stale writes with 409. A delayed older GET cannot move an observed revision backwards after an acknowledged save. Migration returns the keys actually filled, so a local edit while migration is in flight can advance its expected revision only for a key filled by that migration, not a concurrent device's edit.
- Pending edits use unique per-edit localStorage records, retained separately for each tab owner with a sessionStorage identifier. Web Locks prevent a cloned/reloaded tab from claiming a live tab's owner; each successful acknowledgement removes only its own record. A failed old edit is not replayed over a newer device's revision. Multiple uncertain same-key records remain intact and are presented as a conflict with the latest choice displayed. If Web Locks are unavailable, recovery of an inherited pending owner fails closed with an alert rather than automatically replaying. Legacy pending records from the previous branch version remain readable. No automatic live push across devices.
- Browser values migrate once per origin, filling only absent server keys; server values win. Startup theme/sidebar defaults are not writes. A cache/storage failure is visible; a browser with blocked storage cannot retain its fallback across reloads. **Known limitation:** there is no in-UI conflict resolution action; conflicting records and edits are retained for manual inspection. A fresh unrelated tab does not automatically claim a closed tab's pending records. Restore the original browser tab/session to recover those records. These limitations require independent review before acceptance.
- Shared: theme, last/recent programs, archived flag, sidebar, finding sorting, dashboard and report-view preferences, Recent/Submissions list fields, and Terminal Settings (copy switches, shortcut and default dock). Excluded: drafts, report content, credentials, tab locks, terminal network exposure, and free-text search recents. Current terminal dock and maximize state stay in sessionStorage; terminal open/size state remains browser-local and is not sent to the server.
