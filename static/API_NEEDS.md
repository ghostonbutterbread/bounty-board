# Frontend integration contract

`api.js` is the transport seam. The frontend does not write report sources, even if a report-write capability is advertised. Metadata writes still require their explicit capability and same-origin endpoint. Program roots and filesystem access are configured server-side; the browser does not collect secrets or paths.

## Read

`GET /api/data` can return HTTP 202 with `portfolio.state: "loading"` and no `programs`. The frontend polls with capped backoff. A completed or refreshing snapshot is HTTP 200 with `portfolio` status, last-update timestamp and any error; the previous snapshot stays visible while refreshing or after an error. A refreshing snapshot is stale display only; its identity is not proof of the live root. The Refresh button requests a new scan with `X-Portfolio-Refresh: 1`. HTTP 503 with no snapshot is unavailable, not an empty portfolio. Legacy synchronous JSON without ready status or a nonempty scan token can be displayed, but cannot authorize actions. See `BACKEND_API.md` for the complete contract.

Completed JSON:

```json
{"programs":[{"id":"stable-program-id","name":"Program name","family":"Family","lanes":[{"name":"Web","findings":[],"coverage":[],"gadgets":[],"map":[],"reports":[],"warnings":[]}]}],"warnings":[]}
```

Arrays are scoped to the lane. Missing collections are shown as unavailable, not zero; warnings are shown verbatim as text. The backend returns findings as `fid`, `class_name`, `title`, `severity`, `status` (also `submission`, `submission_status`, `platform_outcome`); `api.js` maps `fid` and `class_name` to UI identity and class. Coverage may be an array or `{items, counts, total, mapped_kinds, unclassified_surfaces}`. The object is preserved: mapped inventory, assessment counts and questions are shown separately, and evidence references are escaped text rather than active links. Neither inventory nor an empty assessment list implies complete testing. A coverage, map or gadget item can be an object or string. Reports may include `{path,name,kind,owner_fids,editable}`; the selector shows the relative path and supplied ownership without inferring it for older `{path,name}` records. Selecting a path fetches `GET /api/report?family=...&program=...&lane=...&path=...` with `X-Portfolio-Source` set to the displayed ready snapshot's `source_token`, which returns `{content,revision,editable:false}`; the current backend rejects absent, stale, or unverified tokens with 409. A directly embedded report may instead provide `id`, `title`, `content` (Markdown), and `revision`. An explicit `editable:false` prevents writes even if a capability is advertised. `revision` must be an opaque token for the exact source content, not merely a timestamp guess.

Dashboard statistics count only loaded records. Counts do not imply unique findings across lanes or a test-depth/coverage metric. The severity breakdown preserves recorded values, counts missing severities separately, and labels partial data when discovery or finding collections are incomplete. Missing lane or finding arrays make finding totals unknown. `root_unavailable` or `discovery_incomplete` warnings make portfolio totals unknown; report source warnings likewise make the report total unknown. Submission state and result are displayed only from the explicitly recorded `submission.state` and `submission.result` fields; finding status is never used to infer a submission or outcome.

The BBH metadata adapter also accepts the backend's opt-in `capabilities.finding_metadata: true` and `finding_fields` list. It sends `PATCH /api/finding` with `{family,program,lane,fid,patch}`, `X-Requested-With: Bounty-Board`, and the displayed `source_token` in `X-Portfolio-Source`; it verifies the returned finding ID and field value. Severity and status use the backend's documented value sets; class uses a text field. Severity rationale is always displayed when present; when `severity_rationale` is advertised it can be edited and explicitly saved for that finding. The backend remains responsible for source validation and persisted verification. The UI warns that uncoordinated local or sync edits can be overwritten; capability advertisement is not a concurrency guarantee. Failed or unverified writes may have changed the source, so the UI asks for refresh. No BBH capability means no BBH write request. This feature branch remains incomplete and metadata writes must stay disabled pending the race work in the integration dossier.

## Proposed optional capabilities

A backend opts in by adding a top-level `capabilities` object. No capability means read-only. This proposed contract must be coordinated with the backend; absent coordination no update is sent. The named route is an example, not a hard-coded frontend endpoint.

```json
{"capabilities":{
  "findingMetadata":{"enabled":true,"method":"PATCH","url":"/api/finding-metadata","options":{"severity":["High","Low"],"class":["XSS"],"status":["Draft"]}},
  "reportWrite":{"enabled":true,"method":"PATCH","url":"/api/report"}
}}
```

- `findingMetadata`: only a stable finding ID and fields with advertised options are editable. Request: `{programId,lane,findingId,field,value}`; success response: `{value}` with the persisted value. The server owns validation, concurrency and ledger consistency. If a backend cannot guarantee the update addresses the correct source record, it must not advertise this capability. The frontend rejects an unconfirmed or mismatched `value` and displays an error.
- `reportWrite`: a prospective contract only, not consumed by the UI. Source writing remains disabled until every actual source writer can participate in a proven shared conditional-write protocol. A revision check followed by rename is not an atomic compare-and-swap.

Report edits autosave synchronously to browser-local storage, keyed by the backend's `root_identity`, program ID, lane and report ID. The identity is a canonical-path hash, not a secret, and changes if the root moves. When identity is unavailable or invalid, edits remain in this tab only and must be copied before leaving or refreshing. Legacy unscoped v1 entries are left intact and are never automatically assigned to a root; recover them manually from browser storage only after determining their origin. The locally vendored EasyMDE editor does not use its own autosave: that implementation removes empty drafts and clears data on form submit. The board stores the draft together with its original content and source revision and retains empty drafts. A changed source revision is shown as a conflict without overwriting the draft. The explicitly labelled save-to-report control remains disabled. Drafts are local to the browser profile and origin; clearing site data loses them, and they may contain sensitive material accessible to local browser users. Storage errors and unrecognized stored data are shown rather than overwritten; copy edits before leaving if persistence fails. Each write checks the previously observed stored value, and storage events block a tab after another tab changes the same draft. These checks are not an atomic compare-and-swap: genuinely simultaneous writes can still overwrite one another. A blocked tab retains its edits in memory and warns the user to copy them. An unsaved draft triggers a before-unload warning where supported. Markdown preview supports headings, paragraphs, bold, emphasis, inline/code fences and lists; raw HTML is escaped and links/images are rendered as text, so the preview cannot trigger external fetches. It is intentionally not a complete Markdown implementation.

The frontend makes no claims of live file watching, external revision polling, report triage, or submission. Conflicts are checked on loading or refreshing report content, not continuously. The backend must independently secure routes, restrict exposure, validate requests and protect writes; a UI capability flag is not authorization.

## Verification

`node --test static/tests/app.test.cjs` uses Playwright, synthetic in-memory fixtures and, for backend integration cases, disposable synthetic roots and a synthetic writer. It does not require real bounty files. Set `CHROME_BIN` when Chrome is not installed at `/usr/bin/google-chrome`. The metadata backend integration case requires explicit backend write opt-in and must not be run without the appropriate fixture safety approval.
